# 주차별 이론 강의 개요 (30–40분) — 초안

> **분량 원칙:** 기본 30분, 내용 많은 주는 40분까지(발표 전환 시간에서 흡수).

> **근거 자료:** `materials/repos/` — Berkeley CS294 슬라이드(뼈대) · MS ai-agents-for-beginners(강의노트 서술) · HF agents-course · Anthropic cookbook(데모).

## W1. 에이전트 개요 + ReAct

**한 줄 목표:** "LLM이 어떻게 *행동하는 시스템*이 되는가"를 ReAct 루프 하나로 이해한다.

**핵심 개념**
1. LLM 단독의 한계 — 정적 지식, 행동 불가, 일회성 응답
2. 에이전트의 정의 — LLM + 도구 + 루프; **워크플로우 vs 에이전트** 자율성 스펙트럼
3. CoT — "생각을 말로 하게 하면 성능이 오른다" (다음 주 예고)
4. **ReAct 루프** — Thought → Action → Observation 반복, 왜 추론과 행동을 섞으면 둘 다 좋아지나

**진행 개요 (35′)**
- 0–5′ 왜 지금 에이전트인가 — Deep Research·Claude Code 등 실물 데모/사례 1개
- 5–15′ 정의와 스펙트럼: 고정 파이프라인 ↔ 완전 자율, "LLM이 제어 흐름을 결정하는가"
- 15–25′ CoT → ReAct 계보: 추론만 / 행동만 / 둘을 교차 — 세 가지 비교 표
- 25–32′ ReAct 트레이스 한 편을 **라이브로 같이 읽기** (HotpotQA 예시)
- 32–35′ 연결: 오늘 실습 = 이 루프를 while문으로 직접 구현(`loop.py`); 발표 = ReAct·CoT 원 논문

**자료:** Berkeley `intro.pdf`·`llm_agent_history.pdf` · MS lesson 01·03 · HF unit1

## W2. 추론 모델 (Reasoning Models)

**한 줄 목표:** "생각을 더 시키는" 두 갈래 — 추론 시간에(test-time) vs 학습으로(내재화) — 를 구분한다.

**핵심 개념**
1. Test-time compute — best-of-N, **self-consistency**(다수결), 더 오래 생각 = 더 정확
2. **STaR** — 모델이 만든 추론 흔적으로 자기 자신을 학습(부트스트랩)
3. **R1/RLVR** — 정답 검증 가능한 보상만으로 추론이 *창발*한 이야기 (aha moment)
4. 에이전트 설계 함의 — 추론모델은 언제 쓰나(비용·지연 트레이드오프)

**진행 개요 (37′)** — *RL 사전 지식 없음을 가정*
- 0–5′ 복습+문제 제기: CoT는 공짜였다 — 더 밀어붙이면?
- 5–15′ test-time compute 스케일링: 같은 모델, N배 샘플 → 정확도 곡선 보기
- 15–29′ 학습으로 내재화: STaR 루프 그림 → **RL 3분 입문(강아지 비유·SFT 대조, 수식 0)** → R1 훈련 스토리(보상 서사로)
- 29–34′ o1/R1 시대의 에이전트: "루프를 짧게, 생각을 길게"? 비용 표로 비교
- 34–37′ 연결: 실습 = self-consistency 구현(`reasoning.py`); 발표 = STaR·DeepSeek-R1

**자료:** Berkeley `inference_time_techniques_lecture_sp25.pdf`·`llm-reasoning.pdf`·`Jason-Weston-Reasoning.pdf`·`OLMo-Tulu-Reasoning-Hanna.pdf`

## W3. 도구 사용 (Tool Use)

**한 줄 목표:** function calling의 내부 동작을 단계별로 해부해 "마법이 아니라 파싱"임을 안다.

**핵심 개념**
1. Function calling 파이프라인 — 스키마 제공 → 모델이 호출 의도 출력 → 파싱 → 실행 → 결과 재주입
2. 좋은 도구 정의 — 이름·설명·파라미터가 곧 프롬프트; 도구 문서화 = 프롬프트 엔지니어링
3. 실패 모드 — 잘못된 인자, 없는 도구 호출, 에러 처리·재시도
4. 도구를 *배우는* 두 접근 — Toolformer(자가 라벨링) vs ToolLLM(대규모 실제 API)

**진행 개요 (35′)**
- 0–5′ 문제 제기: 말만 하는 모델 → 계산기 하나 못 쓴다 (환각 산수 데모)
- 5–17′ function calling 내부: 실제 API 요청/응답 JSON을 화면에 띄워 한 단계씩
- 17–25′ 도구 스키마 설계 원칙 + 흔한 실패 모드 (라이브: 나쁜 설명 → 오호출)
- 25–32′ 논문 프리뷰: 도구 사용을 프롬프트가 아니라 *학습*으로 — 두 논문 대조
- 32–35′ 연결: 실습 = 도구 레지스트리·파서(`tools.py`); MCP는 W7에서

**자료:** MS lesson 04(tool-use) · anthropic-cookbook `tool_use/` · Berkeley `agentworkflows.pdf`

## W4. 계획과 탐색 (Planning & Search)

**한 줄 목표:** "한 발씩 greedy"의 한계를 보고, 분해·계획·탐색이라는 세 가지 처방을 배운다.

**핵심 개념**
1. 과제 분해(task decomposition) — 복잡한 질문 → 하위 단계
2. **Plan-then-execute vs interleaved(ReAct)** — 계획을 미리 다 세울 때의 장단
3. **ToT** — 추론을 트리 탐색으로: 후보 생성 + 자기 평가 + BFS/DFS (직관 수준)
4. **ReWOO** — 관찰을 계획에서 분리하면 토큰 비용이 준다 (효율 관점)

**진행 개요 (35′)**
- 0–5′ 문제 제기: ReAct는 greedy — 한 번 잘못 들어가면 못 돌아온다 (실패 트레이스)
- 5–15′ 분해와 계획 패턴: 분해 프롬프트, plan-execute-replan 루프
- 15–25′ ToT: Game of 24 예제로 트리 그림 그리며 — 생성기/평가기/탐색 3요소
- 25–32′ ReWOO: 같은 과제의 ReAct vs ReWOO 토큰 수 비교 → 비용 절감 논리
- 32–35′ 연결: 실습 = 질문 분해 플래너(`planner.py`); 발표 = ToT·ReWOO

**자료:** MS lesson 07(planning-design) · Berkeley `language_agents_YuSu.pdf`·`102824-yuandongtian.pdf`

## W5. 자기반성·메타인지 (Reflection)

**한 줄 목표:** "실패를 말로 요약해 다음 시도에 주입"하는 것이 왜 학습처럼 작동하는지 이해한다.

**핵심 개념**
1. 생성 → 비평 → 개선 루프 (**Self-Refine**)
2. **Reflexion** — 언어 피드백을 에피소드 메모리에 쌓는 'verbal RL' (gradient 없이 개선)
3. 피드백의 출처가 관건 — 외부 신호(테스트 통과, 도구 에러) vs 순수 자기 비평
4. 자기교정 논쟁 — 외부 신호 없는 self-correction은 종종 안 된다 (한계 균형 있게)

**진행 개요 (30′)**
- 0–5′ 문제 제기: 첫 시도에 틀렸다 — 사람은 다시 본다, 에이전트는?
- 5–13′ Self-Refine 루프: 같은 모델이 생성자·비평자·수정자 역할 — 예시 1개 정독
- 13–22′ Reflexion: 구조도(Actor–Evaluator–Self-Reflection) + "언어가 gradient를 대신"
- 22–27′ 언제 되고 언제 안 되나: 검증 가능한 과제 vs 개방형 과제
- 27–30′ 연결: 실습 = 실패→피드백→재시도(`reflect.py`); 발표 = Reflexion·Self-Refine

**자료:** MS lesson 09(metacognition) · `agentic_ai_andrew`(reflection 패턴)

## W6. RAG 1부: 기초

**한 줄 목표:** 임베딩 검색의 원리와 RAG 파이프라인 전체를, 수식 최소로 손에 잡히게 만든다.

**핵심 개념**
1. 파라메트릭 지식의 한계 — 환각, 지식 컷오프, 출처 없음 → 비파라메트릭 보강
2. **임베딩·코사인 유사도** — "의미를 좌표로" (이 과목에서 유일하게 수식 나오는 날)
3. 파이프라인 — 청킹 → 임베딩 → 인덱스 → top-k 검색 → 컨텍스트 주입 → 생성
4. **HyDE** — 질문과 문서는 생김새가 다르다 → 가짜 답을 만들어 검색

**진행 개요 (40′)** *(중간 데모 포함, 이 주는 길게)*
- 0–5′ 문제 제기: 우리 랩 내부 문서를 물어보면? (환각 데모)
- 5–15′ 임베딩: 2차원 그림으로 직관 → 코사인 유사도 한 줄 수식 → numpy 5줄
- 15–27′ 파이프라인 단계별 + **청킹이 품질을 좌우** (크기/오버랩 선택 데모)
- 27–34′ RAG 원 논문의 위치(2020) + HyDE 아이디어 그림 하나로
- 34–40′ 연결: 실습 = `retriever.py` — **오늘부터 최종 앱의 심장을 만든다** 강조
  *(보안 복선 1줄: "오늘 만든 문서 입구가 W14에서 공격 통로가 된다" — 예고만)*

**자료:** `RAG_Techniques`(기초 노트북) · Berkeley `MKA.pdf` · MS lesson 12 일부

## W7. 에이전틱 RAG + MCP

**한 줄 목표:** "항상 검색"에서 "필요할 때 검색"으로 — 검색을 도구로 만들고, 도구 생태계 표준(MCP)을 본다.

**핵심 개념**
1. 고정 파이프라인 RAG의 낭비 — 상식 질문에도 검색, 잘못된 검색에 무방비
2. **에이전틱 RAG** — 검색=도구, 에이전트가 *언제·무엇을·다시* 검색할지 결정 (멀티홉)
3. **Self-RAG / Adaptive-RAG** — 반성 토큰으로 검색·생성 품질 자평 / 질문 복잡도 라우팅
4. **MCP** — 도구 연결의 USB-C: 호스트–클라이언트–서버 구조, 왜 표준이 필요한가

**진행 개요 (35′)**
- 0–5′ 문제 제기: 지난주 RAG에 "안녕?"이라고 하면 벌어지는 일
- 5–15′ 에이전틱 RAG 패턴 지도: 라우팅 → 자기평가 → 멀티홉 (그림 1장씩)
- 15–23′ 논문 프리뷰: Self-RAG의 반성 토큰 / Adaptive-RAG의 복잡도 분류기 — 대조
- 23–32′ MCP: 프로토콜 구조도, 도구 N×M 문제 → 표준화, 실제 MCP 서버 데모 1개
- 32–35′ 연결: 실습 = retriever를 W3 도구 레지스트리에 등록 — **두 모듈이 처음 만난다**

**자료:** MS lesson 05(agentic-rag)·11(agentic-protocols) · HF unit3 · GenAI `mcp-tutorial.ipynb`

## W8. 컨텍스트 엔지니어링 (하네스) ⭐

**한 줄 목표:** 컨텍스트 윈도우를 *희소 자원*으로 보고 예산 관리하는 눈을 기른다.

**핵심 개념**
1. "더 긴 컨텍스트"가 답이 아니다 — **Lost in the Middle** 위치 편향(U자 곡선)
2. 컨텍스트 해부 — 시스템 프롬프트 / 도구 정의 / 히스토리 / 검색 결과, 각각의 예산
3. 관리 전략 3종 — **선별**(관련성 필터) · **정렬**(중요한 것을 양끝에) · **압축**(요약, LLMLingua)
4. 컨텍스트 실패 모드 — poisoning·distraction·confusion; 실제 하네스(Claude Code 등)의 대응

**진행 개요 (35′)**
- 0–5′ 문제 제기: 문서 20개를 다 넣었더니 오히려 답이 나빠졌다 (실측 그래프)
- 5–15′ Lost in the Middle 실험 정독: U자 곡선이 말하는 것, 몇 위에 둘 것인가
- 15–25′ 예산 관리 전략: 선별·정렬·압축 각각 예시 — LLMLingua 압축 전/후 비교
- 25–32′ 프로덕션 하네스 사례: 실제 코딩 에이전트의 컨텍스트 구성 뜯어보기
- 32–35′ 연결: 실습 = 토큰 예산·정렬·압축(`context.py`) — 지난주 검색 결과가 입력
  **🏁 중간 데모 체크포인트:** W8까지가 from-scratch 단일 에이전트의 완성형 — 실습 말미 '내 에이전트 중간 데모'로 중간 점검을 대신한다

**자료:** Berkeley 관련 강연 · Anthropic context-engineering 자료 · MS lesson 12(context-engineering)

## W9. 메모리 (Memory)

**한 줄 목표:** "컨텍스트 ≠ 메모리" — 세션을 넘는 기억의 저장·검색·갱신 설계를 배운다.

**핵심 개념**
1. 단기(대화 버퍼) vs 장기(외부 저장) — 컨텍스트 관리(W8)와의 경계
2. **MemGPT** — OS 비유: 컨텍스트=RAM, 외부 저장=디스크, 에이전트가 스스로 페이징
3. **Mem0** — 프로덕션 메모리 파이프라인: 추출 → 중복/모순 해소 → 갱신(ADD/UPDATE/DELETE)
4. 무엇을 기억할 것인가 — 최신성·중요도·관련성 점수, 그리고 *망각*의 필요

**진행 개요 (30′)**
- 0–5′ 문제 제기: 어제 알려준 내 이름을 오늘 모른다
- 5–14′ MemGPT: 계층 구조도 + function으로 스스로 메모리를 읽고 쓰는 트레이스
- 14–22′ Mem0: 갱신 연산이 왜 어려운가(모순 해소) — 예시 3개
- 22–27′ 검색 기준 설계: recency×importance×relevance (Generative Agents 유산)
- 27–30′ 연결: 실습 = `memory.py`(장기 메모리를 retriever로 재사용 — W6 재등장)

**자료:** MS lesson 13(agent-memory) · GenAI `memory-agent-tutorial.ipynb` · Berkeley `language_agents_YuSu.pdf`

## W10. 멀티에이전트 + LangGraph ⭐ (프레임워크 전환점)

**한 줄 목표:** 협업 아키텍처 패턴을 배우고, 지금까지 손으로 짠 것을 그래프 위에 얹는다.

**핵심 개념**
1. 왜 나누나 — 역할 특화, 컨텍스트 분리(한 에이전트에 다 넣으면 W8 문제 재발)
2. 아키텍처 패턴 — supervisor/router · handoff · debate · 파이프라인(SOP)
3. **AutoGen vs MetaGPT** — 자유 대화형 협업 vs 절차(SOP) 강제형 협업
4. **그래프 실행 모델** — 노드(우리 모듈)·엣지(제어 흐름)·상태(명시적 딕셔너리); "감싸기, 버리기 아님"

**진행 개요 (40′)** *(전환점이라 길게)*
- 0–5′ 문제 제기: 에이전트 하나에 도구 20개 — 무엇이 무너지는가
- 5–15′ 패턴 지도: supervisor/handoff/debate 그림 3장, 각각 언제 쓰나
- 15–23′ 논문 프리뷰: AutoGen의 대화 프로그래밍 vs MetaGPT의 SOP — 철학 대조
- 23–35′ **LangGraph 실행 모델**: 우리 `loop.py`가 그래프로 변신하는 과정을 코드로 나란히
- 35–40′ 연결: 실습 = W1–9 모듈을 노드로 감싸기(`graph.py`) — 전환의 이유와 범위 명시

## W12. 에이전트 강화학습 (개념)

**한 줄 목표:** 프롬프트로 안 되는 개선을 *학습*으로 — RL의 언어를 에이전트 용어로 번역한다. *(수식 최소)*

**핵심 개념**
1. 왜 RL인가 — 정답 시연 없이도 "잘 된 결과"에서 배우기; 프롬프트 개선의 천장
2. MDP를 에이전트 말로 — 상태=컨텍스트, 행동=토큰/도구 호출, 보상=과제 성공
3. 보상 설계 — 결과 보상 vs 과정 보상, RLHF → **RLVR**(검증 가능 보상; W2 R1과 연결)
4. **ReTool** — "언제 코드 도구를 쓸까"를 RL로 배우기 — 에이전틱 RL의 현재

**진행 개요 (30′)**
- 0–5′ 문제 제기: W5 반성은 세션 안에서만 — 모델 자체를 좋게 하려면?
- 5–15′ RL 개념 번역: 에이전트 루프 그림에 상태·행동·보상 라벨 붙이기 (수식 0개)
- 15–23′ RLHF→RLVR 계보 + W2의 R1 복습을 여기에 접속
- 23–27′ ReTool: 도구 호출 시점이 학습으로 바뀌는 그래프
- 27–30′ 연결: 실습 = 보상 기반 도구선택 *시뮬레이션* 노트북(학습 아님, 관찰)

**자료:** Berkeley `OLMo-Tulu-Reasoning-Hanna.pdf`·`dawn-agentic-ai.pdf`

## W13. 평가·벤치마크 (Evaluation)

**한 줄 목표:** "몇 점?"이 아니라 "무엇을·얼마 주고·재현 가능하게 재는가"를 묻는 눈을 기른다.

**핵심 개념**
1. 에이전트 평가의 특수성 — 다단계·비결정성·환경 의존 (단일 QA 정확도로 부족)
2. **AI Agents That Matter의 비판** — 비용 축 누락, 리더보드 과적합, 재현 불가
3. 비용–정확도 **Pareto 곡선** — 같은 정확도를 1/10 비용으로 내는 baseline의 충격
4. **τ-bench와 pass^k** — 한 번 성공(pass@k)이 아니라 *k번 모두* 성공(일관성)

**진행 개요 (35′)**
- 0–5′ 문제 제기: 리더보드 1등 에이전트를 가져왔더니 우리 문제에서 엉망
- 5–15′ 평가 설계 축: 능력 vs 회귀, 최종답 vs 궤적, LLM-as-judge의 함정
- 15–25′ 두 논문 프리뷰: Pareto 곡선 그림 정독 + pass^k 정의와 시사점
- 25–32′ 우리 스케일의 평가 하네스: testset·채점기·비용 로깅 설계
- 32–35′ 연결: 실습 = `eval/harness.py` — **최종 발표 때 이 점수표로 방어한다** 예고

**자료:** Berkeley `percyliang.pdf` · MS lesson 10 일부

## W14. 신뢰·보안 (Safety & Security)

**한 줄 목표:** 도구+외부 데이터가 만드는 새 공격면(간접 인젝션)과 구조적 방어를 배운다.

**핵심 개념**
1. 에이전트의 공격면 — 모델 탈옥이 아니라 *시스템* 공격: 도구·데이터·권한
2. **직접 vs 간접 프롬프트 인젝션** — 오염된 문서/웹페이지가 명령이 되는 순간
3. 위험 3요소(lethal trifecta) — 비공개 데이터 접근 × 불신 콘텐츠 노출 × 외부 송신
4. 방어 계층 — 구조적(권한 분리·인간 승인·샌드박스) vs 탐지형(필터·분류기); 완벽한 방어는 없다

**진행 개요 (35′)**
- 0–7′ **라이브 데모**: 오염 문서 하나로 우리 docqa-agent가 탈취되는 장면
- 7–17′ 인젝션 분류 체계: 직접/간접, 주입 경로 지도 (우리 앱 구조도 위에 표시)
- 17–27′ 방어 계층 설계: trifecta 끊기, 최소 권한, 승인 게이트 — 사례별로
- 27–32′ InjecAgent 프리뷰: 공격 성공률 수치가 말하는 것
- 32–35′ 연결: 실습 = `guardrails.py` + 서로의 에이전트 레드팀 (수업 중 공격 교환)

**자료:** MS lesson 06(trustworthy)·18(securing) · Berkeley `antrsp.pdf`·`dawn-agentic-ai.pdf`

## W15. 프로덕션과 단순함 (Production)

**한 줄 목표:** "에이전트가 항상 답은 아니다" — 복잡도를 정당화하는 법과 ACI 설계를 배운다.

**핵심 개념**
1. **Agentless의 교훈** — 고정 3단계 파이프라인이 복잡한 에이전트를 이긴 사건
2. **ACI**(Agent–Computer Interface) — 에이전트용 인터페이스는 사람용과 다르다 (SWE-agent)
3. 프로덕션 체크리스트 — 관측성(로깅·트레이스), 비용·지연 예산, 폴백, 버전 고정
4. 단순함의 원칙 — 워크플로우로 충분하면 워크플로우로; 자율성은 필요한 만큼만

**진행 개요 (35′)**
- 0–5′ 문제 제기: SWE-bench 리더보드에서 벌어진 반전 이야기
- 5–15′ Agentless vs SWE-agent 대조: 같은 문제, 정반대 철학 — 표 하나로
- 15–23′ ACI 설계 원칙: 검색·편집 인터페이스를 에이전트 친화적으로 바꾼 실험들
- 23–30′ 프로덕션 체크리스트: 한 학기 만든 앱을 체크리스트에 실제로 대보기
- 30–35′ 연결: 실습 = `app.py` 통합 + **단순 파이프라인 baseline과 우리 에이전트 비교**

**자료:** Berkeley `neubig24softwareagents.pdf`·`Burak_slides.pdf` · MS lesson 10(production)

## 공통 운영 규칙

- **여는 5분 = 문제 제기**: 반드시 지난주 산출물(우리 앱)의 *한계*에서 출발 → 이번 주가 그 처방
- **닫는 3분 = 연결**: 오늘 실습 모듈 + 오늘 발표 논문이 강의의 어느 개념에 꽂히는지 명시
- **매주 '현장 노트' 3–5분 (★필수)**: 논문 서사(Berkeley 축)만으로는 반쪽 — MS 레슨의 practitioner 레이어에서 그 주제의 **실무 용어·프로세스·체크리스트**를 추출해 별도 구간으로. 아래 표가 주차별 목록
- **논문 프리뷰 ≠ 논문 설명**: 강의에서는 핵심 그림 1장·핵심 수치 1개만 — 상세는 학생 발표 몫
- **수식 예산**: 학기 전체에서 W6 코사인 유사도 1개. 나머지는 그림·표·트레이스로
- **데모 우선**: 매주 실패 데모 1개(문제 제기용)가 성공 데모보다 교육 효과가 큼
