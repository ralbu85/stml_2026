## W1. 강의소개 · 에이전트 개요 (What is an Agent?)

**한 줄 목표:** 에이전트를 한 문장으로 정의하고("LLM이 제어 흐름을 결정"), 챗봇이 껍데기일 뿐임(폼팩터)을 안다.

**핵심 개념**
1. LLM 단독의 한계 — 정적 지식, 행동 불가, 일회성 응답
2. 에이전트의 정의 — LLM + 도구 + 루프; **워크플로우 vs 에이전트** 자율성 스펙트럼
3. **폼팩터 4형태** — 대화형·위임형·임베디드·헤드리스 (챗봇은 첫 형태였을 뿐)

**진행 개요 (25′ — 앞에 OT 30′: 평가 방식 + W2~15 발표자·토론자 일괄 배정)**
- 0–5′ 왜 지금 에이전트인가 — Deep Research·Claude Code 등 실물 데모/사례 1개
- 5–15′ 정의와 스펙트럼 + 폼팩터: "LLM이 제어 흐름을 결정하는가"
- 15–21′ 현장 노트: 해부도(Model·Instructions·Tools·Memory)·언제 쓰나·패턴 5종
- 21–25′ 연결: 실습 = 환경 세팅 + 첫 프롬프트; 발표는 W2부터(발표자 배정은 OT에서)

**자료:** Berkeley `intro.pdf` · MS lesson 01·03 · HF unit1 · Anthropic *Building Effective Agents*

## W2. 프롬프팅과 추론 (Prompting & Reasoning)

**한 줄 목표:** "같은 모델, 다른 정답률"이라는 관찰 하나에서 CoT가 도출되는 논증을 세우고, 같은 원리를 계산의 양으로 확장한다(self-consistency·test-time compute).

**핵심 개념**
1. **추론(reasoning)** 의 정의와 에이전트 품질의 상한
2. 직접 질의의 실패 원인 — 글밖에 없는 작업 공간, 환각
3. **CoT** — 중간 단계의 외부화; 유도 수단은 지시(zero-shot)와 풀이 예시(**in-context learning**); 창발 조건과 한계(내부 지식 의존)
4. **Self-consistency** — 표집의 확률적 성질과 다수결의 주변화 논리 (이 과목 유일의 수식 후보)
5. **Test-time compute** — 예측 횟수와 정확도의 교환, 추론 시점 스케일링, 비용 축

**진행 개요 (40′)** — 원본은 `lectures/week02/notes.md`(교재 산문)
- 0–5′ 문제 제기: 추론의 정의 → 같은 모델·같은 문제, 묻는 방식에 따른 정오 (CoT 논문 Figure 1 실측)
- 5–12′ 원인: 작업 공간이 글뿐 → 답 직행 시 모든 단계가 예측 하나에 몰림
- 12–21′ 처방: 재주입 → 중간값의 보존 → 유도 수단(지시·예시) = CoT; 창발
- 21–26′ 한계: 내부 지식 의존(환각 잔존) — Apple Remote 실측 → W4·W5 예고
- 26–35′ 확장: 표집 → self-consistency(다수결이 근사하는 것, 정답 수렴·오답 분산) → test-time compute 방법군과 비용
- 35–40′ 연결: 실습 = CoT·exemplar 정답률 실험(다수결 구현은 W3 실습); 발표 = CoT (첫 학생 발표, 1편)

**자료:** Berkeley `llm-reasoning.pdf`·`inference_time_techniques_lecture_sp25.pdf` · Anthropic prompt engineering tutorial

## W3. 추론 모델과 강화학습 (Reasoning Models & RL)

**한 줄 목표:** test-time compute의 내재화로 추론 모델을 정의하고, 시연 데이터 없이 추론 능력을 가중치에 넣는 두 경로(STaR 부트스트랩 · 강화학습)를 세운다.

**핵심 개념**
1. **추론 모델**(o1/R1) — 호출자 절차의 내재화, thinking budget, 일반 모델과의 선택 기준
2. 훈련의 문제 — 과정 레이블 부재와 결과 정오의 비대칭; **STaR**(자가 생성·정오 필터·재학습)
3. **강화학습** — 정책·보상의 정의, 목적식 $J(\theta)$와 정책 기울기(기준선 문제 포함), 지도학습(모방)과의 차이, **RLHF vs RLVR**
4. **R1** — 규칙 보상 RL, **GRPO**(그룹 상대 어드밴티지·목적식), 긴 추론의 창발; 보상 해킹·증류

**진행 개요 (35′)** — *RL 사전 지식 없음 가정, 정의부터 강의에서 세운다*
- 0–5′ 문제 제기: W2 다수결은 호출자의 절차다 — 이산 답 전제·과제별 설계·일률 N배 비용
- 5–12′ 내재화: 추론 모델과 thinking budget, 일반 모델과의 선택(측정 근거 → W13)
- 12–18′ 훈련의 문제와 STaR: 풀이 시연의 부재, 결과 정오 필터의 부트스트랩과 그 한계(모방의 상한)
- 18–26′ 강화학습: 정책·보상 정의, 목적식과 정책 기울기(보상이 큰 응답의 로그확률을 올린다), 기준선, 보상의 두 출처(RLHF 선호 근사 · RLVR 규칙 검증)
- 26–32′ R1: R1-Zero 설계와 GRPO(그룹 상대 어드밴티지 수식), 창발 관찰, 증류와 보상 해킹
- 32–35′ 연결: 실습 = `reasoning.py`(다수결 구현 — 호출자 절차의 실물, N=1 대비 정확도·비용); 발표 = STaR·DeepSeek-R1

**자료:** Berkeley `Jason-Weston-Reasoning.pdf` · Lilian Weng *Why We Think* · DeepSeek-R1 논문 §1–2

## W4. 도구 사용 (Tool Use)

**한 줄 목표:** function calling의 내부 동작을 단계별로 해부해 "마법이 아니라 파싱"임을 안다.

**핵심 개념**
1. Function calling 파이프라인 — 스키마 제공 → 모델이 호출 의도 출력 → 파싱 → 실행 → 결과 재주입
2. 좋은 도구 정의 — 이름·설명·파라미터가 곧 프롬프트; 도구 문서화 = 프롬프트 엔지니어링
3. 실패 모드 — 잘못된 인자, 없는 도구 호출, 에러 처리·재시도
4. 도구를 *배우는* 두 접근 — Toolformer(자가 라벨링) vs ToolLLM(대규모 실제 API)

**진행 개요 (35′)**
- 0–5′ 문제 제기: 추론(W2–3)은 세웠다 — 말만 하는 모델은 계산기 하나 못 쓴다 (환각 산수 데모)
- 5–17′ function calling 내부: 실제 API 요청/응답 JSON을 화면에 띄워 한 단계씩
- 17–25′ 도구 스키마 설계 원칙 + 흔한 실패 모드 (라이브: 나쁜 설명 → 오호출)
- 25–32′ 논문 프리뷰: 도구 사용을 프롬프트가 아니라 *학습*으로 — 두 논문 대조
- 32–35′ 연결: 실습 = 도구 레지스트리·파서(`tools.py`) — 단발 왕복; 다음 주 이 레지스트리 위에서 루프가 돈다; MCP는 W11에서

**자료:** MS lesson 04(tool-use) · anthropic-cookbook `tool_use/` · Berkeley `agentworkflows.pdf`

## W5. 에이전트 루프 (ReAct)

**한 줄 목표:** 도구 왕복(W4)을 반복 구조로 확장해 첫 완전한 에이전트를 완성한다.

**핵심 개념**
1. **에이전트 루프** — 결정권(다음 행동·종료)의 코드→모델 이양; 워크플로우에서 에이전트로
2. Act-only의 실측 실패와 진단 — 판단이 글에 적히지 않으면 과제 상태가 무너진다
3. **ReAct** — 매 턴 Thought·Action·Observation; 접지(grounding)
4. 트레이스 리딩 — 루프의 실행 기록을 읽고 실패 지점을 찾는 절차 (에이전트 디버깅의 기본)

**진행 개요 (35′)** — 원본은 `lectures/week05/notes.md`(교재 산문)
- 0–5′ 문제 제기: 단일 왕복(W4)으로 안 풀리는 질문 — Apple Remote (W2 한계의 회수)
- 5–13′ 확장: 결정권의 이양 → 에이전트 루프; 반복문 하나와 분기 셋
- 13–22′ 실패와 처방: Act-only 실측 → 진단(W2 원리) → ReAct 규약·성공 트레이스 정독
- 22–28′ 한계(내부 지식 충분 질문에선 CoT 우세 — 정직한 실측)와 운용(max_steps·트레이스 리딩)
- 28–35′ 연결: 실습 = ReAct 루프(`loop.py`) — W4 도구 레지스트리 위에서 첫 완전한 에이전트; **미니 evalset 도입**(이후 매주 5문항); 발표 = ReAct (1편)

**자료:** Berkeley `llm_agent_history.pdf` · MS lesson 03 · ReAct 원 논문

## W6. 검색 증강 (RAG) — 기초와 에이전틱

**한 줄 목표:** 임베딩 검색의 원리와 파이프라인을 세우고, 같은 주 안에서 "항상 검색"을 "필요할 때 검색"(검색=도구)으로 전환한다.

**핵심 개념**
1. 파라메트릭 지식의 한계 — 환각, 지식 컷오프, 출처 없음 → 비파라메트릭 보강
2. **임베딩·코사인 유사도** — 의미의 좌표화, 대조 학습·bi-encoder; 파이프라인(청킹→인덱스→top-k→주입); 하이브리드(BM25+RRF)·재순위화(cross-encoder)·recall@k
3. **에이전틱 RAG** — 고정 파이프라인의 낭비 → 검색=도구, 에이전트가 언제·무엇을·다시 검색할지 결정
4. **Self-RAG** — 반성 토큰으로 검색 여부·품질 자평 (발표 위임)

**진행 개요 (40′)** *(통합 주라 길게)*
- 0–5′ 문제 제기: W5 에이전트는 돈다 — 우리 랩 내부 문서를 물어보면? (환각 데모)
- 5–14′ 임베딩: 2차원 그림 직관 → 코사인 유사도 한 줄 수식 → 파이프라인 단계별(청킹이 품질을 좌우)
- 14–22′ 고정 파이프라인의 낭비("안녕?"에도 검색) → 검색을 도구로: 라우팅·멀티홉
- 22–30′ 논문 프리뷰: RAG 원 논문의 위치(2020) + Self-RAG 반성 토큰; HyDE·Adaptive-RAG는 선택읽기 안내
- 30–40′ 연결: 실습 = `retriever.py` 구현 + W4 레지스트리에 검색 도구 등록 — W5 루프가 필요할 때만 검색
  *(보안 복선 1줄: "오늘 만든 문서 입구가 W14에서 공격 통로가 된다" — 예고만)*

**자료:** `RAG_Techniques`(기초 노트북) · MS lesson 05(agentic-rag) · Berkeley `MKA.pdf` · HF unit3

## W7. 계획과 탐색 (Planning & Search)

**한 줄 목표:** "한 발씩 greedy"의 한계를 보고, 분해·계획·탐색이라는 처방을 배운다.

**핵심 개념**
1. 과제 분해(task decomposition) — 복잡한 질문 → 하위 단계
2. **Plan-then-execute vs interleaved(ReAct)** — 계획을 미리 다 세울 때의 장단
3. **ToT** — 추론을 트리 탐색으로: 후보 생성 + 자기 평가 + BFS/DFS (직관 수준)
4. **ReWOO** — 관찰을 계획에서 분리하면 토큰 비용이 준다 (효율 관점)

**진행 개요 (35′)**
- 0–5′ 문제 제기: ReAct(W5)는 greedy — 멀티홉 검색 질문에서 한 번 잘못 들어가면 못 돌아온다 (우리 앱의 실패 트레이스)
- 5–15′ 분해와 계획 패턴: 분해 프롬프트, plan-execute-replan 루프
- 15–25′ ToT: Game of 24 예제로 트리 그림 그리며 — 생성기/평가기/탐색 3요소
- 25–32′ ReWOO: 같은 과제의 ReAct vs ReWOO 토큰 수 비교 → 비용 절감 논리
- 32–35′ 연결: 실습 = 멀티홉 검색 질문 분해 플래너(`planner.py`) — W6 검색 도구 위에서; 발표 = ToT·ReWOO

**자료:** MS lesson 07(planning-design) · Berkeley `language_agents_YuSu.pdf`·`102824-yuandongtian.pdf`

## W8. 자기반성·메타인지 (Reflection)

**한 줄 목표:** "실패를 말로 요약해 다음 시도에 주입"하는 것이 왜 학습처럼 작동하는지 이해한다.

**핵심 개념**
1. 생성 → 비평 → 개선 루프 (**Self-Refine**)
2. **Reflexion** — 언어 피드백을 에피소드 메모리에 쌓는 'verbal RL' (gradient 없이 개선)
3. 피드백의 출처가 관건 — 외부 신호(검색 품질, 도구 에러, 테스트 통과) vs 순수 자기 비평
4. 자기교정 논쟁 — 외부 신호 없는 self-correction은 종종 안 된다 (한계 균형 있게)

**진행 개요 (30′)**
- 0–5′ 문제 제기: 검색이 빗나간 첫 시도 — 계획(W7)을 세워도 첫 시도는 틀린다
- 5–13′ Self-Refine 루프: 같은 모델이 생성자·비평자·수정자 역할 — 예시 1개 정독
- 13–22′ Reflexion: 구조도(Actor–Evaluator–Self-Reflection) + "언어가 gradient를 대신"
- 22–27′ 언제 되고 언제 안 되나: 검증 가능한 과제 vs 개방형 과제
- 27–30′ 연결: 실습 = 검색 실패→피드백→재시도(`reflect.py`); 발표 = Reflexion·Self-Refine

**자료:** MS lesson 09(metacognition) · `agentic_ai_andrew`(reflection 패턴)

## W9. 컨텍스트 엔지니어링 (하네스) ⭐

**한 줄 목표:** 컨텍스트 윈도우를 *희소 자원*으로 보고 예산 관리하는 눈을 기른다.

**핵심 개념**
1. "더 긴 컨텍스트"가 답이 아니다 — **Lost in the Middle** 위치 편향(U자 곡선)
2. 컨텍스트 해부 — 시스템 프롬프트 / 도구 정의 / 히스토리 / 검색 결과, 각각의 예산
3. 관리 전략 — **선별**(관련성 필터) · **정렬**(중요한 것을 양끝에, 프롬프트 캐시) · **압축**(요약, LLMLingua 정보량 기준)
4. 컨텍스트 실패 모드 — poisoning·distraction·confusion; 실제 하네스(Claude Code 등)의 대응

**진행 개요 (35′)**
- 0–5′ 문제 제기: 검색(W5–6)·계획(W7)·반성(W8)이 컨텍스트를 폭발시켰다 — 문서 20개를 다 넣었더니 오히려 답이 나빠졌다 (실측 그래프)
- 5–15′ Lost in the Middle 실험 정독: U자 곡선이 말하는 것, 몇 위에 둘 것인가
- 15–25′ 예산 관리 전략: 선별·정렬·압축 각각 예시 — LLMLingua 압축 전/후 비교
- 25–32′ 프로덕션 하네스 사례: 실제 코딩 에이전트의 컨텍스트 구성 뜯어보기
- 32–35′ 연결: 실습 = 토큰 예산·정렬·압축(`context.py`) — 검색 결과가 입력
  **🏁 중간 데모 체크포인트:** W9까지가 from-scratch 단일 에이전트의 완성형 — 실습 말미 '내 에이전트 중간 데모'로 중간 점검을 대신한다

## W10. 메모리 (Memory)

**한 줄 목표:** "컨텍스트 ≠ 메모리" — 세션을 넘는 기억의 저장·검색·갱신 설계를 배운다.

**핵심 개념**
1. 단기(대화 버퍼) vs 장기(외부 저장) — 컨텍스트 관리(W9)와의 경계
2. **MemGPT** — OS 비유: 컨텍스트=RAM, 외부 저장=디스크, 에이전트가 스스로 페이징
3. **Mem0** — 프로덕션 메모리 파이프라인: 추출 → 중복/모순 해소 → 갱신(ADD/UPDATE/DELETE)
4. 무엇을 기억할 것인가 — 최신성·중요도·관련성 점수, 그리고 *망각*의 필요

- 5–14′ MemGPT: 계층 구조도 + function으로 스스로 메모리를 읽고 쓰는 트레이스
- 14–22′ Mem0: 갱신 연산이 왜 어려운가(모순 해소) — 예시 3개
- 22–27′ 검색 기준 설계: recency×importance×relevance (Generative Agents 유산)
- 27–30′ 연결: 실습 = `memory.py`(장기 메모리를 retriever로 재사용 — W5 재등장)

## W12. 추론 경제성 (Inference Economics)

**한 줄 목표:** 에이전트가 소모하는 추론(호출·토큰·지연)을 정확도와 나란히 놓는 설계 축을 세우고, 과정 전체에 흩어진 test-time compute 교환을 하나의 원리로 통합한다.

**핵심 개념**
1. 비용의 구조 — 호출 수 × 토큰(입력/출력) × 티어 단가; 입력의 제곱 누적(W9)·추론 토큰(W3)
2. 비용–정확도 교환 — test-time compute 통합(W2 다수결·W3 thinking budget·W7 탐색·W8 반성), 수확 체감, **compute-optimal** 배분과 파레토 경계
3. 절감 수단 — 모델 라우팅·캐스케이드, 프롬프트/의미 캐시, 컨텍스트 경제(W9), 예산 정책(max_steps·토큰 예산·thinking budget)
4. 측정 — 비용을 일급 지표로, 정확도/비용 파레토 → W13 평가로 확장

**진행 개요 (30′)**
- 0–6′ 문제 제기: 능력마다 곱해지는 추론 비용(루프·멀티에이전트·탐색·반성·컨텍스트) — 정확도만 보면 새는 곳
- 6–13′ 비용 구조: 호출·토큰·티어 인자 분해, 5턴 루프 비용 계산으로 입력 누적 확인
- 13–21′ 교환 원리: 흩어진 test-time compute를 하나로, 수확 체감·compute-optimal·파레토
- 21–27′ 절감 수단: 라우팅/캐스케이드·캐싱·예산 정책
- 27–30′ 연결: 실습 = 질문 유형별 경로 라우팅(내부 문서 vs 웹) — 라우팅의 실물; 발표 = Snell·FrugalGPT

**자료:** DeepMind `Snell-test-time-compute.pdf` · `FrugalGPT.pdf` · Anthropic prompt caching 문서

## W13. 평가·벤치마크 (Evaluation)

**한 줄 목표:** "몇 점?"이 아니라 "무엇을·얼마 주고·재현 가능하게 재는가"를 묻는 눈을 기른다.

**핵심 개념**
1. 에이전트 평가의 특수성 — 다단계·비결정성·환경 의존 (단일 QA 정확도로 부족)
2. **AI Agents That Matter의 비판** — 비용 축 누락, 리더보드 과적합, 재현 불가
3. 비용–정확도 **Pareto 곡선** — 같은 정확도를 1/10 비용으로 내는 baseline의 충격
4. **τ-bench와 pass^k** — 한 번 성공(pass@k)이 아니라 *k번 모두* 성공(일관성)

**진행 개요 (35′)**
- 0–5′ 문제 제기: 리더보드 1등 에이전트를 가져왔더니 우리 문제에서 엉망
- 5–15′ 평가 설계 축: 능력 vs 회귀, 최종답 vs 궤적, LLM-as-judge의 함정
- 15–25′ 두 논문 프리뷰: Pareto 곡선 그림 정독 + pass^k 정의와 시사점
- 25–32′ 우리 스케일의 평가 하네스: testset·채점기·비용 로깅 설계 — W4부터 쌓아 온 미니 evalset의 정식화
- 32–35′ 연결: 실습 = `eval/harness.py` — **최종 발표 때 이 점수표로 방어한다** 예고

**자료:** Berkeley `percyliang.pdf` · MS lesson 10 일부

## 공통 운영 규칙

- **여는 5분 = 문제 제기**: 반드시 지난주 산출물(우리 앱)의 *한계*에서 출발 → 이번 주가 그 처방
- **닫는 3분 = 연결**: 오늘 실습 모듈이 강의의 어느 개념에 꽂히는지 명시 (발표 논문은 디커플링 — 관련 주차의 개념 등장 이후 배치)
- **매주 '현장 노트' 3–5분 (★필수)**: 논문 서사(Berkeley 축)만으로는 부족 — MS 레슨의 practitioner 레이어에서 그 주제의 **실무 용어·프로세스·체크리스트**를 추출해 별도 구간으로. 아래 표가 주차별 목록
- **논문 프리뷰 ≠ 논문 설명**: 강의에서는 핵심 그림 1장·핵심 수치 1개만 — 상세는 학생 발표 몫
- **수식**: 대학원 수업이므로 이해에 필요하면 쓴다(개수 제한 없음 — 2026-07-13 수식 예산 폐기). 현재 사용처: W2 self-consistency 주변화, W3 RL 목적식·정책 기울기·GRPO, W6 코사인 유사도. 수식은 반드시 기호를 말로 푸는 문장과 병기하고, 유도의 세부는 발표로 위임할 수 있다
- **데모 우선**: 매주 실패 데모 1개(문제 제기용)가 성공 데모보다 교육 효과가 큼
- **미니 evalset**: W5부터 매주 실습에 5문항 평가 포함 — 트레이스를 보고 개선하는 습관, W13에서 정식화

## 주차별 '현장 노트' — 실무 용어·프로세스 지도 ★

각 주 덱을 만들 때 이 칸을 소진할 것.

| 주 | 실무 키워드 | 프로세스/체크리스트 |
|---|---|---|
| 1 | 에이전트 해부도(Model·Instructions·Tools·Memory), system prompt, role(system/user/assistant/tool), context window, temperature, 워크플로우 패턴 5종(chaining·routing·parallelization·orchestrator-workers·evaluator-optimizer) | **언제 에이전트를 쓰나/안 쓰나** 체크리스트 (MS L1) |
| 2 | 프롬프트 템플릿, few-shot 예시 설계, 시스템 프롬프트 구조화 | 프롬프트 개선 절차: 한 번에 하나 바꾸고 매번 측정 |
| 3 | reasoning effort / thinking budget(벤더별 이름), 생각 토큰 과금, 스트리밍, 모델 라우팅 | **모델 선정 순서도**: 검증가능?→다단계?→예산?→eval로 전후 비교 |
| 4 | 도구 스키마(JSON Schema), `tool_choice`, 병렬 도구 호출, structured outputs, 타임아웃·재시도·멱등성 | 좋은 도구 정의 체크리스트(이름·설명·인자·에러 메시지) · 도구 실패 대응 절차 |
| 5 | 트레이스(trace)·스텝·스크래치패드, max_steps·루프 가드, Final Answer 파싱, 미니 evalset | 트레이스 리딩 = 에이전트 디버깅의 기본 절차 |
| 6 | 청킹 전략(크기·오버랩), 임베딩 모델 선택, top-k·유사도 임계값, 벡터 스토어 지형, 하이브리드 검색(BM25+벡터)·리랭커 | 인덱싱 파이프라인 절차 · RAG 개선 순서: 검색부터 고쳐라 |
| 7 | plan-and-execute, replanning, 서브태스크 분해(DAG), human-in-the-loop 승인 지점 | 계획 검토 게이트: 실행 전 계획을 사람/검증기에 보이는 절차 |
