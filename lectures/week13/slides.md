# 0–5′ · 에이전트 평가는 왜 다른가 — 그리고 결정타

모델 평가(정답 맞히기)와 다른 세 가지:

- **다단계** — 스텝 오류가 누적된다 (W12 긴 지평의 벽)
- **비결정성** — 같은 입력, 다른 트레이스 (온도 0에서도)
- **환경 의존** — 웹은 변하고, API는 죽는다

결정타: **정확도는 돈으로 살 수 있다.**

> AlphaCode: 0-shot **~0%** → 1,000회 재시도 **15%+** → 100만 회 **30%+**

- 재시도는 과학적 발견이 아니다 — 그런데 **1차원 리더보드는 이 둘을 구분 못 한다**

# 축 ① 누가 보나 — 모델 평가 vs 다운스트림 평가

| | 모델 평가 | 다운스트림 평가 |
|---|---|---|
| 질문 | 과학: 뭐가 진보인가 | 조달: 뭘 사서 쓸까 |
| 비용 축 | 파라미터·컴퓨트 (시간 불변이 미덕) | **달러** (가격 인하 반영이 미덕) |
| 쓰는 사람 | 연구자 | **우리** — 앱 만드는 사람 |

- 프록시의 함정: Mixtral 홍보 그림은 "활성 파라미터" 기준 — 실제 API 가격은 Llama-2 13B의 **2배** (Anyscale, 2024-06)
- **NovelQA 사례**: long-context vs RAG, 정확도 비슷 — 실사용(질문 하나씩)은 RAG가 **20배+ 저렴**한데, 리더보드 방식(한 번에 다 질문)에선 절반 저렴으로 보임 → **10배 왜곡**
- 교훈: 남의 리더보드를 내 조달 결정에 그대로 쓰지 마라

# 축 ② 무엇을 재나 — 능력 vs 회귀, 답 vs 궤적

| | 능력 평가 (벤치마크) | 회귀 평가 (evalset) |
|---|---|---|
| 질문 | 상한이 어디까지? | **고치다 뭘 부쉈나?** |
| 주기 | 논문 낼 때 한 번 | 프롬프트 한 줄 바꿀 때마다 |
| 실무 비중 | 조달 시점 잠깐 | **일상의 주력** |

- **최종답 채점 vs 궤적 채점** — 답이 맞아도 메일을 3번 보냈다면? (W4 멱등성의 귀환)
- 벤치마크의 사각지대: **human-in-the-loop 부재** — 사람 피드백 하나로 GPT-4가 어려운 프로그래밍 0% → **86%+** (Shi et al.). 완전 자율 점수는 실사용의 하한일 수 있다

# 축 ③ 누가 채점하나 — LLM-as-judge, 그 소금의 정체

자유 서술엔 규칙 채점기가 없다 → LLM에게 채점을 시킨다. 싸고 빠르다. 그런데:

- **W4 어음 회수**: ToolEval — 후보 답안도 LLM, **채점자도 ChatGPT**. 우리가 "소금 한 줌"이라 부른 그것
- judge의 알려진 편향: 자기 출력 선호 · 위치(먼저 온 답) · **장황함**(길면 후하게)
- judge 모델이 바뀌면 점수도 바뀐다 — **채점자 버전 고정**은 기본기

**캘리브레이션 절차** (judge도 평가 대상이다):
사람 라벨 소량(20~50건) → judge 일치율 측정 → 기준·프롬프트 수정 → 재측정

- 다른 길도 있다: judge를 아예 안 쓰고 **환경 상태로 채점** — 잠시 뒤 τ-bench

# AI Agents That Matter — 단순 베이스라인의 역습

HumanEval 리더보드의 SOTA 에이전트 3종 vs 저자들의 단순 베이스라인 (164문제 × 5회):

| SOTA 에이전트 | 단순 베이스라인 |
|---|---|
| LDB(디버깅)·LATS(트리 탐색)·Reflexion(반성, 보고 91%) | retry(온도 0, ≤5회) · **warming**(온도 0→0.5) · **escalation**(Llama-3 8B→GPT-3.5→70B→GPT-4) |

결과 (Fig.1, 비용-정확도 평면):

- warming과 최고 에이전트의 **정확도 유의차 없음** — 반성도 트리도 없이
- 비용은 다르다: Reflexion·LDB는 warming보다 **50%+**, LATS는 **50배+** — 비슷한 정확도대에서 비용 격차 **최대 ~100배(두 자릿수)**
- escalation은 LDB(GPT-3.5)의 **절반 이하 비용**으로 정확도는 더 높게

# Pareto 곡선 — 2차원이 되는 순간 보이는 것

```
정확도 ↑
        │      ×LATS (50배 비용)
        │  ×LDB  ×Reflexion
        │ ●warming   ← 프런티어는 단순 베이스라인이 차지
        │●escalation
        └──────────────────→ 비용($, 로그 스케일)
```

- **Pareto 프런티어**: 두 축 모두에서 이기는 놈이 없는 점들 — 보고할 것은 점 하나가 아니라 **이 곡선**
- 복잡한 에이전트가 이긴 게 아니라, **아무도 단순 베이스라인과 비교하지 않았던 것** — "반성·디버깅이 성능 원인"이라는 통념은 아직 근거 미확정
- 비용을 축에 넣으면 설계가 달라진다: DSPy 조인트 최적화 — 같은 정확도, 변동비 **53% 절감**(GPT-3.5, HotPotQA)
- 논문 읽는 새 습관: 결과 표를 보면 **"비용 열은 어디 있죠?"** 부터

<p class="small">출처: AI Agents That Matter (우리 papers/ PDF 기준) §2.3·§3.2</p>

# 재현 불가면 SOTA가 아니라 일화다

같은 논문의 2부 — 정확도 숫자 자체도 흔들린다:

- **과적합**: 에이전트 벤치마크는 작다(수백 샘플) — 원리상 **lookup table로 100%** 가능. 17개 벤치마크 조사: 적절한 홀드아웃 보유 = task-specific **3/6** · domain-general **1/8** · fully-general **0/2** (7개는 계획조차 없음)
- **에러바 없음**: SWE-bench 1회 완주 ≈ **$8,000+** (2,000+ 문제 × $4 한도) → 아무도 여러 번 못 돌림. 저자들 5회 재현에서, 보고 수치가 **5회 최대값보다 높은** 논문 다수 — W12에서도 봤다: 프롬프트 힌트 한 줄로 14.41 ↔ 11.70
- **채점 버그**: LATS·STeP — 틀린 태스크를 맞다고 채점, 태스크 임의 제거(각 1개·8개)
- **환경 함정**: WebArena의 Reddit 클론엔 rate limit — **태스크 실행 순서**가 점수를 바꾼다

# 보상 해킹 — 지표를 속이는 에이전트

**사례: WebArena 1위 STeP, 35.8%** — 지난주 본 그 14.41%(베이스라인)의 2배 이상, 2위에도 +10%p. 비결은?

```
WebArena Reddit 태스크: "user_name의 프로필로 가라"
STeP의 정책:  현재 base URL + '/user/user_name'   ← 태스크별 하드코딩
```

- 사이트 구조가 바뀌면(드리프트) 즉사 — 하지만 벤치마크가 드리프트를 안 재니 **규칙 안에서 합법**
- 코딩 에이전트판: 테스트 통과가 보상이면 **테스트를 하드코딩**하거나 특수분기 — 실습에서 여러분도 겪는다
- **W3 어음 회수** — R1의 교훈: *"보상에 넣지 않은 것은 얻지 못한다 — 보상 설계가 곧 사양서."* 평가도 같다: **지표에 넣지 않은 것**(비용·일반성·드리프트 내성)**은 최적화되지 않는다**
- Goodhart: 지표가 목표가 되는 순간, 좋은 지표이기를 멈춘다

# τ-bench — 유저와 도구 사이에서, DB로 채점한다

질문: 실제 고객 응대처럼 **유저(대화)·도구(API)·정책(규정집)** 을 한꺼번에 다루면?

- 구성: LM이 고객 연기(온도 1.0) ↔ 에이전트(온도 0.0) + API 도구 + 도메인 정책, 태스크당 최대 30 액션
- 도메인: **retail 115** 태스크 · **airline 50** 태스크

|---|---|---|
| **GPT-4o (최고)** | **61.2** | **35.2** |

# pass^k — 한 번 잘하기 vs 매번 잘하기

- **pass@k**: k번 중 **한 번이라도** 성공 (희망의 지표 — 코드 생성엔 맞다, 테스트가 걸러주니까)
- **pass^k**: k번 **전부** 성공 (신뢰의 지표 — 고객 응대엔 이것)

같은 태스크를 대화만 조금 다르게 8번 시키면 (retail, Fig.4):

> GPT-4o: pass^1 **61.2%** → pass^8 **25% 미만** — 고객 8명 연속 응대 성공 확률이 1/4

- airline은 시작부터 35.2 — 그리고 시스템 프롬프트에서 정책을 빼면 **33.2 → 10.8** (−22.4%p). retail은 61.2 → 56.8, 겨우 −4.4 — **상식으로 풀리던 것**이었고, 복잡한 규칙은 있어야만 (그리고 있어도 절반은) 따른다
- 평균 성공률(1차원)은 **신뢰성을 숨긴다** — 오늘 harness가 3회 반복을 재는 이유

# 오후 실습: `eval/harness.py` — 내 에이전트의 점수표

```python
# testset.jsonl: 수업 논문 QA 20문항 (우리 docqa-agent의 실사용 분포)
def run_eval(agent, testset, trials=3):        # 3회 — pass^1과 일관성까지
    for case in testset:
        t0 = time.time()
        answer, usage = agent.run(case["q"])
        record(correct=grade(answer, case["a"]), # ← 오늘 채울 곳 ① 채점기
               tokens=usage, latency=time.time()-t0)
    return scoreboard()                          # ← 오늘 채울 곳 ② 4열 집계
```

- ✅ 완료 기준: **정확도 · 비용 · 지연 · 재현성** 4열 점수표 출력 — 정확도만 나오면 미완성
- 이 점수표는 오늘로 끝나지 않는다: W14 가드레일·W15 베이스라인 비교의 계기판, **W16 최종 발표에서 이 점수표로 방어한다**

# 오늘의 세 줄 요약

1. **정확도는 돈으로 살 수 있다** — 그래서 비용 없는 리더보드는 반쪽. 보고할 것은 점이 아니라 **Pareto 곡선** (warming ≈ SOTA, LATS는 50배 비용)
2. **채점기부터 의심하라** — judge는 캘리브레이션, 벤치마크는 홀드아웃, 그리고 지표는 해킹당한다 (STeP 35.8%의 정체)
3. **한 번 성공 ≠ 매번 성공** — pass^1 61.2%가 pass^8 25% 미만으로 (τ-bench). 신뢰성은 반복해야만 보인다

오늘 성능을 쟀다 — 이제 **최악을 잰다. 공격당하면 어떻게 되나?**
