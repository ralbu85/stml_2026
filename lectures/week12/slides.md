# 도입 — 오류 복리의 산수

스텝당 성공률이 **90%**로 꽤 훌륭한 에이전트가 있다고 하자:

| 스텝 수 | 태스크 성공률 (0.9ⁿ) |
|---|---|
| 1 | 90% |
| 10 | **34.9%** |
| 30 | **≈ 4.2%** |

- 웹 태스크는 보통 **10–30+ 스텝** — "항공권 검색해서 제일 싼 걸 예약해"
- 스텝 하나하나는 잘하는데, **곱하면 무너진다** — 긴 지평(long horizon)의 수학
- 오늘 볼 벤치마크 성적표(에이전트 10%대)는 이 산수의 실측판이다

# API 없는 세계

W4에서 도구를 배웠다 — 하지만 도구에는 전제가 있었다: **API가 있어야 한다.**

- 세상 소프트웨어의 대부분은 API가 없다 — **GUI만 있다**
  (사내 ERP, 항공사 예약 화면, 엑셀, 관공서 웹사이트…)
- 발상의 전환: 소프트웨어마다 API를 만들어 주는 대신,
  **사람의 인터페이스(화면·마우스·키보드)를 에이전트가 그대로 쓰게 하자**
- 그러면 **모든 소프트웨어가 도구가 된다** — 범용성의 극대화
- 대가: 오늘 내내 볼 난이도 — 관찰은 거대하고, 행동은 잘게 쪼개지고, 지평은 길어진다

# 같은 루프, 새 도메인

새 알고리즘이 아니다 — **W2의 ReAct 루프 그대로**, 관찰과 행동만 바뀐다:

| | docqa-agent (W2–11) | 컴퓨터/웹 에이전트 |
|---|---|---|
| 관찰 | 도구가 돌려준 텍스트 | **화면** (DOM·접근성 트리·스크린샷) |
| 행동 | JSON 도구 호출 | **클릭·타이핑·스크롤** |
| 스텝 수 | 한 자릿수 | **10–30+** (오류 복리 구간) |
| 실패 비용 | 재시도하면 됨 | **비가역일 수 있음** (구매·발송·삭제) |

- Thought → Action → Observation 사이클은 동일 — 하네스가 브라우저/OS로 바뀔 뿐
- 그래서 오늘의 질문은 둘: **① 화면을 어떻게 관찰로 만드나 ② 행동을 어떻게 정의하나**

# 관찰 — 화면을 보여주는 세 가지 방법

같은 웹페이지를 에이전트에게 세 가지로 줄 수 있다 (WebArena가 셋 다 지원):

| 표현 | 무엇 | 특징 |
|---|---|---|
| **스크린샷** | RGB 픽셀 배열 | 사람이 보는 것과 동일 |
| **DOM 트리** | HTML 전체 구조 | 정확하지만 방대·중복 |
| **접근성 트리 (a11y tree)** | DOM의 부분집합 — 역할·텍스트·속성만 | 스크린리더용 구조를 재활용 |

- 접근성 트리 = 원래 시각장애인 스크린리더를 위한 표준 —
  "화면의 의미 구조"만 남긴 요약본이라 에이전트 관찰로 인기
- 각 요소에 **ID**를 붙이면 "click [1582]"처럼 좌표 없이 지칭 가능

# DOM·접근성 트리 vs 스크린샷 — 트레이드오프

| | DOM·접근성 트리 | 스크린샷 |
|---|---|---|
| 모델 요구 | 텍스트 LLM으로 충분 | 멀티모달(VLM) 필수 |
| 요소 지칭 | **ID로 클릭** — grounding 쉬움 | **좌표 예측** — grounding 어려움 |
| 커버리지 | 웹·a11y 지원 앱만 | **화면에 보이는 모든 것** (캔버스·데스크톱 앱) |
| 약점 | 길고 중복 — 원본 XML은 수백만 토큰, 필터링 필수 | 고해상도·요소 밀집에 취약 |
| OSWorld 성적 | 2.37–12.24% | 5.26–5.80% |

- 절충안 **Set-of-Marks(SoM)**: 스크린샷 위에 번호 박스를 그려 "3번 클릭"으로 —
  단, OSWorld에선 요소가 너무 많아 오히려 **하락**하기도
- 결론: **어느 쪽도 아직 답이 아니다** — 성적표가 증명 (21분 구간)

<p class="small">출처: OSWorld 논문 (우리 papers/ PDF 기준) §4.1–4.2 · Table 5</p>

# 행동 공간 설계

행동을 **몇 개의 무엇으로 줄 것인가** — 하네스 설계자의 결정:

| | WebArena | OSWorld |
|---|---|---|
| 행동 | `click [id]` `type [id] [text]` `scroll` `goto [url]` … | **pyautogui 코드 문자열** (좌표·키 입력) |
| 추상화 | 높음 — 요소 ID 기반, 좌표 불필요 | 낮음 — 픽셀 좌표까지 모델이 |
| 범용성 | 웹 한정 | OS 전체 (모든 앱) |

- 키보드+마우스를 **이산 행동 집합으로 에뮬레이션** — 설계 축은 하나:
  **추상화를 올리면 쉬워지고, 내리면 넓어진다**
- W4 도구 스키마 설계와 같은 문제의 재판(再版) — "행동 공간 = 모델에게 주는 언어"

# 벽 ① — Grounding: "로그인 버튼"을 좌표로

> 계획: "로그인 버튼을 클릭한다" — 좋다. 그래서 **어디를** 클릭하는데?

- **Grounding** = 언어("로그인 버튼")를 화면 위의 실제 요소/좌표로 잇는 문제
- 계획은 맞는데 클릭이 빗나가면 태스크는 실패 — **추론이 아니라 지각이 병목**
- OSWorld의 진단: 최고 모델이 12.24%에 그친 주요인은
  **GUI grounding과 조작 지식(operational knowledge)** 부족
- a11y 트리(ID 지칭)는 이 문제를 우회하는 목발 — 그래서 텍스트 입력이 아직 유리

<p class="small">출처: OSWorld 논문 (우리 papers/ PDF 기준) Abstract · §5</p>

# 벽 ② — 긴 지평, 비가역, 그리고 조기 포기

- **오류 복리** (도입 카드): 스텝당 90%여도 30스텝이면 ≈4.2% — 스텝 수 자체가 적
- **비가역 행동**: 트리 탐색으로 성능을 올릴 수 있지만(상대 +51%),
  "구매 완료" 버튼은 **되돌릴 수 없다** — 탐색이 금지되는 지점 <span class="small">(Berkeley 강의자료 기준)</span>
- **조기 포기**: WebArena에서 "불가능하면 멈춰라" 힌트를 주자
  GPT-4가 **가능한 태스크의 54.9%를 '불가능'으로 오판** — 지시문 한 줄이 성적을 좌우
- **동적 페이지**: 관찰이 매 스텝 변한다 — 팝업·로딩·A/B 테스트

W5(계획)·W6(반성/오류 복구)이 필요한 이유가 이 도메인에서 전부 극대화된다.

# 현장 노트 ① — 웹 에이전트 인프라 용어 5

| 용어 | 무엇 | 왜 알아야 하나 |
|---|---|---|
| **헤드리스 브라우저** | 화면 없이 구동하는 브라우저 (Playwright·Selenium) | 웹 에이전트의 표준 실행기 |
| **접근성 트리** | 스크린리더용 의미 구조 | 에이전트 관찰의 사실상 표준 |
| **액션 스페이스 설계** | 행동을 몇 개의 무엇으로 줄 것인가 | 하네스 설계의 핵심 결정 (앞 슬라이드) |
| **rate limit · robots.txt** | 호출 속도 제한 · 크롤링 허용 규칙 | 예의이자 차단 회피 — 어기면 IP 밴 |
| **샌드박스** | VM/컨테이너 격리 실행 | 에이전트의 손이 닿는 범위를 물리적으로 제한 |

- OSWorld가 **VM 위**에서 도는 이유 = 샌드박스: 비가역 행동도 스냅샷으로 되돌린다

# 현장 노트 ② — 웹 도구 안전 절차

오늘 오후 `tools_web.py`에 그대로 적용할 기본기:

1. **도메인 화이트리스트** — 허용 목록(예: arxiv.org) 밖 URL은 fetch 자체를 거부
2. **읽기전용 기본** — GET만. 쓰기 행동(POST·구매·발송)은 별도 승인 게이트 뒤로
3. **샌드박스 실행** — 에이전트 프로세스가 파일시스템·네트워크 전체에 손대지 못하게
4. **rate limit 준수 + 로깅** — 어디를 언제 긁었는지 전부 기록

> ⚠️ **보안 복선 (예고만):** 오늘 붙인 웹 도구가 **W14 간접 프롬프트 인젝션의 주 통로**다 —
> 웹페이지의 텍스트가 그대로 우리 컨텍스트에 들어온다. 오염된 페이지 = 오염된 프롬프트.

# 오늘의 세 줄 요약

1. **같은 루프, 새 도메인** — 컴퓨터 사용은 새 알고리즘이 아니라 W2 루프의 일반화:
   관찰=화면(DOM/접근성 트리/스크린샷), 행동=클릭·타이핑
2. **병목은 지각과 지평** — grounding(어디를 클릭?)과 오류 복리(0.9³⁰≈4.2%),
   관찰 표현(DOM vs 스크린샷)은 어느 쪽도 아직 답이 아니다
3. **현실 점검** — 사람 78.24%/72.36% vs 에이전트 14.41%/12.24%:
   사람에겐 쉬운 것이 에이전트에겐 벽이다
