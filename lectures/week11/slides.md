# 우리 에이전트의 현재 — 한 명이 전부 다 한다

W10까지 쌓은 docqa-agent의 시스템 프롬프트 안에는 지금:

```
페르소나 + 계획 지침(W5) + 반성 지침(W6) + RAG 지침(W7–8)
+ 도구 스키마 × N개(W4) + 컨텍스트 규칙(W9) + 메모리 요약(W10)
```

도구 20개짜리 단일 에이전트에서 무너지는 것 네 가지:

1. **선택 정확도** — 비슷한 도구가 많을수록 오선택 (W4 '도구 절벽' 그대로)
2. **컨텍스트 예산** — 스키마·지침이 창을 잠식 (W9에서 측정했던 그 문제의 재발)
3. **지침 응집성** — 비평가 지침과 작성자 지침이 한 프롬프트 안에서 서로 밟는다
4. **디버깅** — 무엇이 잘못돼도 용의자가 하나뿐이라, 역설적으로 원인을 못 좁힌다

# 왜 나누나 — 역할 특화, 그리고 컨텍스트 분리

- **역할 특화**: 검색 담당·코드 담당·비평 담당 — 각자 *자기 도구와 자기 지침만* 갖는다
- **컨텍스트 분리**: 각 에이전트의 창에는 자기 일에 필요한 것만
  → 도구 20개 문제가 "도구 5개 × 4명"으로 바뀐다 — W9 처방의 구조적 버전
- 이미 본 적 있다: **W1 워크플로우 패턴 5종의 orchestrator–workers**
  — 그때는 *함수 호출*이었고, 오늘은 각 worker가 *루프를 가진 에이전트*로 승격

> 멀티에이전트 = 조직도가 아니라 **컨텍스트 격리 장치**다.
> "누가 무엇을 볼 것인가"를 설계하는 일.

# 패턴 ① Supervisor / Router — 중앙에서 나눠준다

```
                    ┌→ 검색 에이전트   (도구: search, fetch만)
사용자 → Supervisor ─┼→ 코드 에이전트   (도구: run_python만)
                    └→ 작성 에이전트   (도구: 없음 · 긴 문체 지침)
                          ↑ 결과는 모두 Supervisor로 복귀
```

- Supervisor가 분배·취합·종료 판단 — worker는 서로를 모른다
- **언제:** 업무 경계가 명확하고, 중앙에서 통제·관측하고 싶을 때 (가장 무난한 기본형)
- **약점:** Supervisor가 병목이자 단일 실패점 — 그가 헷갈리면 전체가 헷갈린다

# 패턴 ② Handoff — 주도권을 통째로 넘긴다

```
사용자 ↔ 접수 에이전트 ──(handoff)──▶ 환불 전문 에이전트 ↔ 사용자
         "환불 건이네요"               이후 대화의 주인이 바뀐다
```

- Supervisor가 "하청"이라면, handoff는 **"전화 돌려드릴게요"** — 복귀하지 않는다
- 대화의 소유권·이력이 함께 이양된다 (콜센터 라우팅과 동형)
- **언제:** 사용자와의 *대화형* 업무에서 전문 분야가 갈릴 때
- OpenAI Agents SDK가 이것을 1급 개념으로 채택 — 이름도 그대로 `handoff`

# 패턴 ③ Debate · ④ 파이프라인(SOP)

**③ Debate — 합의로 정확도를 산다**
```
에이전트 A ──답──┐
에이전트 B ──답──┼→ 서로의 답을 읽고 수정 → 수렴한 답 채택
에이전트 C ──답──┘
```
- 검증기가 없는 문제(사실성·추론)에서 오류를 상호 상쇄 — 비용은 정직하게 N배
- 선택읽기 논문(Du et al., ICML 2024)이 이 계보의 원전

**④ 파이프라인(SOP) — 순서를 못 박는다**
```
기획 → 설계 → 구현 → 테스트   (역할·순서 고정, 산출물 스키마로 인계)
```
- W1의 chaining이 에이전트로 승격된 것 — 오늘 논문 MetaGPT의 본체

# 그러나 — 멀티가 항상 낫진 않다

| 숨은 비용 | 내용 |
|---|---|
| **토큰 비용** | 에이전트 간 왕복마다 이력 전달 — 호출 수·토큰이 곱으로 |
| **조율 오버헤드** | 전달 과정의 정보 손실 — *전화 게임*. 요약할수록 새고, 다 넘기면 격리가 무의미 |
| **오류 전파** | 상류 에이전트의 착오를 하류가 사실로 믿는다 |
| **디버깅 지평** | 용의자가 1명 → N명 + 대화록. 관측 없이는 지옥 |

- **기본값은 단일 에이전트다** — 컨텍스트 하나로 충분하면 나누지 마라
- 나누는 유일한 정당화: *한 컨텍스트에 담으면 (품질·비용이) 무너질 때*

**💬 오늘 발표 후 토론:** 멀티에이전트가 단일보다 *정말* 나은가? 언제 과한가?

# AutoGen — 협업을 "대화"로 프로그래밍한다

핵심 추상화: **conversable agent** — LLM·도구·사람 무엇이든 *메시지를 주고받는 존재*로 통일하고, 애플리케이션 로직을 **에이전트 간 대화**로 짠다 (conversation programming)

| 실험 | 구성 | 결과 |
|---|---|---|
| MATH (전체 테스트셋) | 내장 에이전트 2개 (assistant + user proxy) | **69.48%** vs GPT-4 단독 55.18% |
| ALFWorld (134 태스크) | 2-에이전트 + **grounding agent** 추가 | 평균 **+15%** |
| OptiGuide 코딩 | Writer / Safeguard 역할 분리 | 위험 코드 식별 F1 **+8%**(GPT-4)·**+35%**(GPT-3.5) |

- 읽는 법: 세 결과 모두 **에이전트 추가 = 하네스 업그레이드** — 모델은 그대로다
- grounding agent가 하는 일: 반복 오류 조짐이 보이면 상식 한 줄을 *대화로* 주입

<p class="small">출처: AutoGen 논문 (우리 papers/ PDF 기준) §2–3 · Figure 4 · A1/A3/A4</p>

# MetaGPT — 협업을 "절차(SOP)"로 못 박는다

사람 소프트웨어 회사의 표준운영절차를 코드화: **PM → 아키텍트 → 프로젝트 매니저 → 엔지니어 → QA**, 역할 간 인계는 자유 대화가 아니라 **구조화 산출물**(PRD·설계도·태스크 목록)로만

| 지표 | GPT-4 단독 | MetaGPT | 피드백 제거 시 |
|---|---|---|---|
| HumanEval Pass@1 | 67.0% | **85.9%** | 81.7% |
| MBPP Pass@1 | — | **87.7%** | 82.3% |

**SoftwareDev (70개 개발 태스크, vs ChatDev):**
실행가능성 **3.75 vs 2.25** (4점 만점) · 토큰/코드 1줄 **124.3 vs 248.9** · 사람 수정 횟수 **0.83 vs 2.5**

- 자연어 대신 문서로 인계하는 이유 = 아까 그 **전화 게임** 차단
- 실행 피드백(테스트 돌려보기)만 빼도 −4.2/−5.4%p — W6 "테스트 > 자기비평" 재확인

# 대조 — 그런데 교훈은 하나다

| | AutoGen | MetaGPT |
|---|---|---|
| 협업 조직 | **자유 대화** — 다음 발화자를 동적으로 | **SOP** — 역할·순서 고정 |
| 인계 형식 | 자연어 메시지 | 구조화 문서 (스키마 강제) |
| 강점 | 유연 — 열린 문제, 사람 개입 쉬움 | 신뢰·재현 — 정형 업무 |
| 약점 | 대화가 산으로 갈 수 있다 | 절차 밖 문제엔 경직 |

- 같은 다이얼의 양 끝: **표현력 ↔ 신뢰성** (제약을 팔아 자유를 사거나, 그 반대)
- 공통 교훈: 성능은 모델이 아니라 **협업의 구조**에서 나왔다
  — "하네스가 성능이다" 테제의 멀티에이전트 버전
- 그리고 이 구조들(라우팅·절차·상태)을 담는 공용 그릇이 다음 구간: **그래프**

# 코드 나란히 — `loop.py`가 그래프가 된다

<div class="cols">
<div>

```python
# W2 · loop.py (우리가 짠 것)
while steps < MAX_STEPS:
    reply = llm(history)
    if is_final_answer(reply):
        return extract_answer(reply)
    obs = run_action(reply)
    history += [reply, obs]
```

- 상태: 지역변수 `history`, `steps`
- 제어: `while` + `if`
- 로직: `llm()` `run_action()` …

<div>

```python
# W11 · graph.py (오늘)
class State(TypedDict):        # 상태 스키마
    history: list
    steps: int

g = StateGraph(State)
g.add_node("llm", call_llm)    # ← 우리 llm()
g.add_node("act", run_action)  # ← 우리 tools.py
g.add_conditional_edges("llm",
    route,                     # ← 우리 parse_step()
    {"act": "act", "end": END})
g.add_edge("act", "llm")       # ← while의 화살표
app = g.compile()
```

# 상태가 명시적이면 공짜로 생기는 것들

우리 `history`는 **지역변수**였다 — 프로세스가 죽으면 끝, 밖에서 볼 수도 없다.
그래프에서는 상태가 **선언된 스키마 + 노드 경계마다의 스냅샷**이다. 그래서:

| 기능 | 내용 | 우리에게 왜 필요한가 |
|---|---|---|
| **체크포인팅** | 노드 사이마다 상태 저장 — 중단 재개, 시간여행 디버깅 | 긴 작업·장애 복구 + **W5 승인 게이트**를 '일시정지'로 구현 |
| **스트리밍** | 노드 단위 이벤트 스트림 — 진행 상황 실시간 방출 | 우리는 `print()`를 심었다. 이제 구조가 방출한다 |
| **관측성** | 트레이스가 노드·엣지 구조로 남는다 | W2 "트레이스 리딩" 이 도구 없이 커진 앱에선 불가능 — **W13 평가·관측 예고** |

> 전부 from-scratch로도 만들 수 있다 — 단지 *전부 우리가 짜야 할 뿐*.
> 프레임워크의 가치 = 이 배관의 표준화이지, 우리 로직의 대체가 아니다.

# 현장 노트 ② — 프레임워크, 쓸까 말까 판단 기준

**채택을 정당화하는 세 가지 (이게 없으면 while문 30줄이 낫다):**

1. **관측성** — 노드 단위 트레이스를 볼 수 있나? 없으면 멀티에이전트 디버깅은 불가능
2. **체크포인트·재개** — 긴 작업, 승인 게이트, 장애 복구가 요구사항에 있나?
3. **팀 표준** — 유지보수할 동료가 아는 도구인가? (벤치마크 승자 < 팀이 아는 것)

**채택 후에도 지킬 것:**

4. **탈출구(eject)** — 로직을 프레임워크 문법에 녹이지 마라. 노드의 '속'은 순수 함수로
   → 우리가 오늘 하는 방식이 정확히 이것 (다음 슬라이드)

- 반대 방향의 경고: 단일 루프 + 도구 몇 개짜리 앱에 그래프 프레임워크는 과잉
- **W15 프로덕션 주에 재론** — 감쌌던 것을 다시 벗겨보며 이 판단을 검증한다

# 전환 원칙 — "감싸기, 버리기 아님"

W2–W10에 손으로 짠 모듈이 그대로 노드의 **속**이 된다:

| 우리 모듈 | 그래프에서의 자리 |
|---|---|
| W2 `loop.py`의 while | 그래프의 **순환 구조** 그 자체 |
| W4 `tools.py` | `act` 노드의 속 |
| W5 `planner.py` | `plan` 노드 |
| W6 반성 루프 | `critic` 노드 (선택) |
| W7–8 `rag.py` | `retrieve` 노드 |
| W9 `context.py` | 노드 진입 전 **상태 가공** 단계 |
| W10 `memory.py` | 체크포인터 곁의 장기 저장 |

- 프레임워크에 넘기는 것은 **오케스트레이션과 상태 관리, 둘뿐**
- 순서가 이랬던 이유: 속을 먼저 만들었기에 — 노드가 우리에게 **블랙박스가 아니다**

# 오늘의 세 줄 요약

1. **나누는 이유는 컨텍스트다** — 역할 특화 = 컨텍스트 격리. 단, 기본값은 여전히 단일 에이전트 (비용·전화 게임·디버깅 지평)
2. **협업의 성능은 구조에서 온다** — 자유 대화(AutoGen, MATH 69.5%)든 절차 강제(MetaGPT, HumanEval 85.9%)든, 이긴 것은 모델이 아니라 조직 방식
3. **감싸라, 버리지 마라** — 로직은 우리 것 그대로, 그래프에는 오케스트레이션·상태만 위임. 프레임워크 이름은 바뀌어도(AutoGen→MAF) 개념은 남는다

**다음 주 (W12. 컴퓨터·웹 사용):**
지금까지 에이전트는 *우리가 만든 도구* 안에서만 살았다 —
이제 **진짜 환경(브라우저·OS)에 풀어놓으면?** 관찰 = 화면, 행동 = 클릭.
같은 루프, 훨씬 낯선 세계. (그리고 사람 70–90% vs 에이전트 10–40%라는 성적표)
