# 지난주 앱에 인사를 해 보자

지난주 완성한 파이프라인: **질문 → 무조건 검색 → top-k 주입 → 생성**

```
User: 안녕하세요?
[retriever] 유사 청크 검색 중... top-3:
  #1 (0.31) "…코사인 유사도는 두 벡터의 사잇각…"
  #2 (0.29) "…청킹 오버랩은 보통 10–20%…"
LLM: 안녕하세요! 코사인 유사도에 대해 궁금하신가요?
```

- 인사에도 검색한다. 관련도 0.31짜리 잡음이 컨텍스트에 들어간다
- **W1 미니체크 3번**: "질문마다 문서를 검색해 붙여넣는 시스템" — 답은 *워크플로우*였다
- 그 복선을 오늘 회수한다: **검색할지를 LLM이 정하면, 그때 에이전트다**

# 0–5′ · 문제 제기

# 고정 파이프라인 RAG의 세 가지 무방비

| 무방비 | 증상 | 필요한 판단 |
|---|---|---|
| **불필요한 검색** | 인사·상식에도 검색 — 잡음 주입, 비용·지연 | 검색을 *할지* |
| **나쁜 검색 결과** | 관련 없는 청크가 와도 그대로 생성 | 결과를 *믿을지* |
| **한 번으로 끝** | "빌리 자일스 출생지의 화폐는?" — 2번 찾아야 답 | *다시·더* 찾을지 |

- 셋 다 같은 뿌리: 파이프라인에는 **판단하는 곳이 없다** — 경로가 코드에 박혀 있다
- 실측: GPT-3.5는 무조건 1회 검색(F1 46.99)이 **검색 안 함(48.56)보다 나쁘다**
- 판단 셋(할지·믿을지·다시 할지)을 LLM에 넘기는 것 = 오늘의 전부

# 5–14′ · 에이전틱 RAG
## 검색이 도구가 되면

# 발상의 전환: 파이프라인 → 루프

```
고정 RAG:      질문 → [검색] → [주입] → [생성] → 답     (경로: 사람이 설계)

에이전틱 RAG:  질문 → ┌─ 에이전트 루프 (W2) ──────────┐
                      │ Thought: 문서를 봐야 하나?      │
                      │ Action:  search_docs("…")  ←──── 도구 (W4)
                      │ Observation: [청크들]           │
                      │ … 부족하면 다시 검색 …          │
                      └→ Final Answer                   (경로: LLM이 결정)
```

- 새 부품이 **하나도 없다**: W2 루프 + W4 도구 레지스트리 + 지난주 `retriever.py`
- 검색이 `calculator` 옆자리에 등록될 뿐 — **우리 앱의 두 모듈이 처음 만나는 주**
- 검색 횟수가 0회(상식)에서 n회(멀티홉)까지 **질문마다 달라진다**

# 패턴 ① 라우팅 — 검색을 *할지*, *어디서* 할지

```
질문 → [분류] ─ 상식/인사      → 검색 없이 바로 생성
             ├─ 우리 문서 질문  → 벡터 검색
             └─ 최신 정보 질문  → 웹 검색 도구
```

- W1 워크플로우 패턴 5종의 **Routing**, 그 예고편("W8 적응형 검색")이 오늘이다
- 분류기는 스펙트럼: 프롬프트 한 줄 ("검색이 필요하면 search를 호출") →
  전용 소형 분류기 (Adaptive-RAG) → 모델 자신의 특수 토큰 (Self-RAG)
- 라우팅만 넣어도 첫 번째 무방비(불필요한 검색)가 사라진다 — **가장 싼 개선**

<!--
[8분] W1 패턴 표를 잠깐 다시 띄우면 좋다 — "Routing 행에 'W8 적응형 검색'이라고 적어뒀었다."
스펙트럼 세 단계가 그대로 오늘 후반부 지도: 프롬프트(실습), 분류기(Adaptive-RAG), 토큰(Self-RAG).
-->

# 패턴 ②③ 자기평가·멀티홉 — *믿을지*, *다시* 할지

**② 자기평가 (self-check):** 검색 결과를 쓰기 전에 되묻는다

```
Observation: [청크 3개]
Thought: #1은 관련 있음. #2, #3은 무관 — 버린다. #1만으로 부족 → 질문을 바꿔 재검색
```

**③ 멀티홉 (multi-hop):** 답이 한 문서에 없으면 검색을 *연쇄*한다

```
Q: 빌리 자일스 출생지의 화폐는?
검색1: "빌리 자일스 출생지" → 벨파스트   검색2: "벨파스트 화폐" → 파운드
```

- 셋 다 하네스 구조는 W2 루프 그대로 — **달라진 건 판단의 주체뿐**
- 비용 경고: 판단·재검색마다 LLM 호출이 늘어난다 → 14′ 논문들이 이 트레이드오프를 정면으로

## 판단을 학습으로: Self-RAG · Adaptive-RAG

# 두 논문, 같은 질문, 다른 위치

> "검색할지·믿을지·다시 할지" — 이 판단을 누가 내리나?

| | Self-RAG (2023) | Adaptive-RAG (2024) |
|---|---|---|
| 판단 주체 | **생성 모델 자신** (특수 토큰) | **외부 소형 분류기** (T5-Large) |
| 판단 시점 | 생성 *도중* 문장마다 | 생성 *전* 질문당 1번 |
| 판단 대상 | 검색 여부 + 결과 품질 + 근거 일치 | 질문 난이도 → 전략 3종 라우팅 |
| 바꾸는 것 | 모델을 재학습 | 모델은 그대로, 앞단만 추가 |

- W4의 구도 재방문: "시키는" 방법(프롬프트) 다음은 "배우는" 방법 — 오늘은 판단을 배운다

# Self-RAG — 반성 토큰 4종

생성 모델의 어휘에 **reflection token**을 추가 — 판단이 곧 *다음 토큰 예측*이 된다:

| 토큰 | 값 | 판단 |
|---|---|---|
| `Retrieve` | yes / no / continue | 지금 검색할까? |
| `IsRel` | relevant / irrelevant | 이 청크, 질문과 관련 있나? |
| `IsSup` | fully / partially / no support | 내 문장이 청크에 근거하나? |
| `IsUse` | 5–1 | 답이 전체적으로 유용한가? |

- 문장(segment)마다: `Retrieve` 판단 → 검색 시 청크별 병렬 생성 → `IsRel`·`IsSup`로 채점해 최선 선택
- 학습: GPT-4의 판단을 critic 모델에 증류(토큰 유형당 4k–20k건) → critic이 학습 코퍼스 15만 건에 토큰을 **오프라인 삽입** → 일반 LM 목적함수로 학습. 추론 때 critic 불필요

# Self-RAG — 결과, 그리고 다이얼

단답 QA 정확도 (PopQA, 장꼬리 지식):

| Llama2-chat 13B | ChatGPT | 검색 붙인 ChatGPT | **Self-RAG 7B** | **Self-RAG 13B** |
|---|---|---|---|---|
| 20.0 | 29.3 | 50.8 | **54.9** | **55.8** |

# Adaptive-RAG — 질문마다 다른 전략 (신호등)

**전략 3종을 미리 깔고**, 소형 분류기(T5-Large)가 질문을 셋 중 하나로 라우팅:

```
질문 → [난이도 분류기] ─ A (쉬움)   → 검색 없이 LLM만
                        ├ B (보통)   → 1회 검색 + 생성
                        └ C (복잡)   → 멀티홉 반복 검색
```

라벨은 **수작업 0건** — 두 소스에서 자동 수집:
1. **결과 기반 (silver):** 세 전략을 다 돌려보고, 가장 싼 성공 전략을 정답 라벨로
2. **데이터셋 편향:** 단일홉 데이터셋 출신 → B, 멀티홉 출신 → C

- W1 패턴 5종의 **Routing**을 학습된 분류기로 구현한 것 — 정확히 그 자리

<p class="small">출처: Adaptive-RAG 논문 (우리 papers/ PDF 기준) §3.2 · Figure 2</p>

<!--

silver 라벨의 발상("돌려보고 싼 성공을 정답으로")은 W3 STaR·W4 Toolformer의 자기 라벨링 계보 — 세 번째 재등장.

# Adaptive-RAG — 결과, 그리고 소금 한 줌

GPT-3.5, 단일홉+멀티홉 6개 데이터셋 평균 (시간은 1회 검색=1.0 기준 상대값):

| 전략 | F1 | 평균 검색 스텝 | 상대 시간 |
|---|---|---|---|
| 항상 멀티홉 | 50.87 | 2.81 | 3.33 |
| **Adaptive-RAG** | **50.91** | **1.03** | **1.46** |

- 멀티홉과 **같은 정확도를 절반 이하 시간에** — 쉬운 질문에 낭비하던 검색을 회수한 것
- 상한 확인: 분류기가 전지(oracle)라면 F1 46.94 → **56.28** (FLAN-T5-XL) — 남은 이득도 라우팅에 있다

**소금:** ① 분류기 정확도는 54.52% — 3지선다에서 이 정도로도 효율이 확 좋아진다는 게 오히려 교훈. ② 같은 벤치마크에서 Self-RAG는 F1 22.98 — 단답 위주로 학습된 탓. **평가 셋이 바뀌면 순위가 뒤집힌다** (W13 예고)

# 현장 노트 — RAG가 나쁘면, 검색부터 고쳐라

현업 철칙: **개선 순서는 검색 → 그다음이 생성.** 프롬프트 만지는 건 마지막이다.

# N×M 문제 — 배선이 폭발한다

우리 `tools.py`의 검색 도구는 **우리 앱 전용**이다. 세상 모두가 이 짓을 반복하면:

```
앱 N개 (Claude·커서·우리 앱…)  ×  도구 M개 (검색·DB·슬랙…)  =  연동 코드 N×M벌
```

**MCP (Model Context Protocol):** 도구 쪽 배선을 표준화한 공개 프로토콜 (Anthropic, 2024.11)

```
표준화 후:  앱 N개 ──[MCP 프로토콜]── 도구 서버 M개   =  구현 N+M벌
```

- 비유: **USB-C** — 노트북마다 전용 충전기(N×M)에서, 단자 하나로(N+M)
- 프린터 드라이버, JDBC, LSP… 성숙한 생태계마다 반복된 수순이 도구에도 온 것

<p class="small">출처: modelcontextprotocol.io 사양 (개념 수준)</p>

# MCP 구조 — Host · Client · Server

```
┌─ Host (에이전트 앱: Claude Desktop, IDE, 우리 앱) ─────────┐
│   LLM + 하네스(루프)                                        │
│   ├─ Client ①  ←── JSON-RPC ──→  Server A (문서 검색)       │
│   └─ Client ②  ←── JSON-RPC ──→  Server B (사내 DB)         │
└─────────────────────────────────────────────────────────────┘
```

| 어휘 | 역할 | 우리 앱에서의 대응물 |
|---|---|---|
| **Host** | LLM을 품은 앱 — 사용자를 만나는 쪽 | `loop.py` 돌리는 우리 앱 |
| **Client** | 서버 1개당 1개씩 여는 연결 담당 | (표준화 전엔 없던 층) |
| **Server** | 도구·데이터를 표준 형식으로 노출 | `tools.py`의 서버 버전 |

- 서버가 제공하는 것 셋: **tools**(호출) · resources(읽기) · prompts(템플릿)

# 도구 카탈로그 — 그리고 우리가 이미 아는 것

접속하면 Host가 서버에 묻는다: **"무슨 도구 있어?"** (`tools/list`)

```json
{"tools": [{
  "name": "search_docs",
  "description": "사내 문서에서 관련 청크를 검색한다. …",
  "inputSchema": {"type": "object", "properties": {"query": …}}
}]}
```

- 이 응답 = **도구 카탈로그** — 어디서 봤더라? **W4 도구 스키마 그대로다**
  (이름·설명·JSON Schema 인자). 하네스는 카탈로그를 받아 모델에게 알릴 뿐
- 그래서 W4 체크리스트가 MCP 시대에도 유효: **도구 정의가 곧 프롬프트**
- ⚠️ 보안 복선: 카탈로그를 *남이 만든 서버*가 채운다면? 설명 문자열이 곧 프롬프트인데,
  그걸 외부가 쓴다 — **W14 (프롬프트 인젝션)에서 정면으로**

# 32–35′ 오후 실습: retriever, `tools.py`에 입주하다 📦

```python
# tools.py — W4에 만든 레지스트리, 그대로
TOOLS["search_docs"] = {
    "func": retriever.search,          # ← 지난주 만든 그 함수
    "description": "업로드된 문서에서 관련 내용을 검색한다. "
                   "문서 내용 질문에만 사용. 인사·일반 상식에는 사용하지 말 것.",
}
```

- 새 코드는 거의 없다 — **등록 한 줄 + 설명 문자열**이 오늘의 엔지니어링
- 라우팅은 어디에? 저 description이 한다 — W4 현장 노트 ① ("언제 안 쓰나"를 써라)의 실전
- ✅ 완료 기준: **상식 질문엔 검색 안 하고, 문서 질문에만 검색한다** (트레이스로 확인)
- 📦 최종 프로젝트 부품 2 — 캡스톤 연구보조 에이전트의 "필요할 때만 찾아 읽는" 능력

**발표 2편:** Self-RAG(판단을 토큰으로) · Adaptive-RAG(신호등 분류기)

# 오늘의 세 줄 요약

1. **"매번 검색"은 워크플로우다** — 검색할지·믿을지·다시 할지를 LLM이 정할 때 에이전틱 RAG (W1 미니체크 3번, 회수 완료)
2. 판단은 **배울 수 있다** — 문장마다 반성 토큰(Self-RAG, PopQA 54.9로 검색 ChatGPT 50.8 추월) 또는 질문마다 난이도 라우팅(Adaptive-RAG, 멀티홉과 같은 F1을 시간 44%에)
3. 도구·검색은 **표준 단자로** — MCP host/client/server, 도구 카탈로그 = W4 스키마의 표준화. 현장에선 **RAG 개선은 검색부터** (하이브리드 → 리랭커 → 라우팅)

**다음 주 (W9. 컨텍스트 엔지니어링 ⭐):**
검색을 잘하게 됐더니 새 문제가 생겼다 — **검색 결과가 너무 많다.**
컨텍스트는 유한 자원이다. 문서 20개를 다 넣으면 답이 좋아질까? (스포일러: 아니다)
🏁 W9 실습 말미 = 내 에이전트 **중간 데모 체크포인트**
