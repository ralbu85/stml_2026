# 지난주 예고: "그 청구서를 오늘 받는다"

W6에서 retriever가 도구가 됐다. 잘 되니까 욕심이 났다 — **top-k 3 → 20**:

```
top-k=3  : 프롬프트  3,200 토큰 · 답 정확
top-k=20 : 프롬프트 14,000 토큰 · 지연 2배 · 답이 오히려 흐릿해짐
```

- 지난주 티저: *"문서 20개를 다 넣으면 답이 좋아질까? (스포일러: 아니다)"* — 오늘 그 증명

# 실험: 내용은 그대로, 위치만 바꾼다

Liu et al. — multi-document QA로 통제 실험:

- 입력 = 질문 1개 + 문서 **10 / 20 / 30개** (정답이 든 문서 1 + 방해 문서들, 20개 ≈ 4K 토큰)
- 조작 변수는 단 하나: **정답 문서의 위치** (1번째 ~ k번째)
- 대상: GPT-3.5-Turbo (4K/16K) · Claude-1.3 (8K/100K) · MPT-30B · LongChat-13B(16K)

기준선 (GPT-3.5-Turbo):

| closed-book (문서 0개) | oracle (정답 문서만 1개) |
|---|---|
| 56.1% | 88.3% |

- 모델이 긴 컨텍스트를 *잘* 쓴다면 → 위치를 바꿔도 성능은 그대로여야 한다

# 결과: U자 곡선

```
정확도
 75 ┤ ●                                   ●
    │   ╲                               ╱
 65 ┤     ╲                           ╱
    │       ●───●───────●───────●───●
 55 ┤ ─ ─ ─ ─ ─ closed-book 56.1% ─ ─ ─ ─ ─
    └──┬──────┬──────┬──────┬──────┬──
      1번째   5번째   10번째   15번째  20번째   ← 정답 문서 위치
```

- **처음(primacy)과 끝(recency)은 잘 쓰고, 중간은 못 쓴다** — 최대 20%p 이상 하락
- 20·30문서 세팅에서 정답이 중간이면 **문서를 아예 안 준 것(56.1%)보다 낮다**
- 문서를 주고도 못 찾는 게 아니라, **줘서 더 나빠질 수 있다**

# 더 긴 창도, 더 많은 문서도 답이 아니다

**① 확장 컨텍스트 모델도 똑같이 못 쓴다**
- GPT-3.5-Turbo 4K vs 16K: 같은 입력이 둘 다 들어가는 구간에서 **곡선이 거의 포개진다**
- 창을 늘리는 건 책상을 넓히는 것 — 책상 정리 습관은 그대로

**② 검색은 좋아지는데 읽기는 포화된다** (open-domain QA 사례 연구)
- 문서 수를 늘리면 retriever recall은 계속 오르지만, 답변 정확도는 **일찍 포화**
- 20개 → 50개: GPT-3.5-Turbo **+~1.5%p**, Claude-1.3 **+~1%p**

> 병목은 이제 검색이 아니라 **읽기** — W6의 "검색부터 고쳐라" 다음 단계는 "넣는 걸 고쳐라"

# 시사점 셋 — 처방의 근거

1. **위치가 성능이다** — 같은 내용도 배치만 바꾸면 20%p가 움직인다
   → 중요한 것은 **양끝에** (처음 또는 끝), 애매한 것만 중간에
2. **추가는 공짜가 아니다** — 관련성 낮은 문서는 0이 아니라 **마이너스**
   → 넣기 전에 **선별**하라 (애매하면 버려라)
3. **질문을 양끝에 두는 트릭** (query-aware contextualization)
   — 질문을 문서 앞*과* 뒤에 모두 넣으면 key-value 검색 과제는 거의 완벽해진다
   — 단, multi-doc QA에서는 효과 미미 — **만능은 아니다**

이 셋이 다음 구간의 **예산 관리 4단계**로 이어진다.

# 현장 노트 ① — 측정: 재보지 않으면 모른다

**컨텍스트 감사 절차: ① 측정 → ② 선별 → ③ 정렬 → ④ 압축.** 1단계는 항상 측정:

| 세입자 | 토큰 (우리 앱, 예시) | 통제 다이얼 |
|---|---|---|
| 시스템 프롬프트 | 500 | 고정·구조화 (현장 노트 ②) |
| 도구 스키마 | 800 | 도구 수 (W3 도구 절벽) |
| 히스토리 (스텝 6) | 2,600 **↗ 계속 증가** | 트리밍·요약 |
| 검색 청크 top-5 | 3,000 | k · 청크 크기 (W5) |
| 질문 + 답변 여유 | 700 | — |
| **합계 / 예산 8,000** | **7,600** | 남은 여유 400 ← 위험 |

- 숫자는 예시 — 핵심은 **tokenizer로 실측**해 이런 표를 만들 수 있느냐
- **토큰 예산**: 모델 한도보다 작게 잡은 우리의 상한 — 한도까지 쓰면 U자 곡선이 응징한다

# 선별과 정렬 — 트리밍 vs 요약, 그리고 양끝

**② 선별** — retriever 점수 임계값·중복 제거로 **넣기 전에** 거른다 (근거: 관련성 낮은 문서 = 마이너스)

**③ 정렬** — U자 곡선을 역이용: 시스템 프롬프트 **맨 앞** · 핵심 문서·지시는 **끝(질문 직전)** · 애매한 것만 중간

**히스토리가 넘칠 때 — 트리밍 vs 요약:**

| | 트리밍 (자르기) | 요약 (줄여 쓰기) |
|---|---|---|
| 방법 | 오래된 스텝·긴 관찰 삭제 | LLM으로 압축 재작성 |
| 비용 | 공짜 | LLM 호출 1회 추가 |
| 위험 | 잘린 정보는 소실 | 요약 오류·왜곡 |
| 적합 | 관찰 꼬리, 오래된 스텝 | 긴 대화 전체의 골자 |

# ④ 압축 — LLMLingua: 토큰을 '지운다'

아이디어: 언어는 원래 중복적이다 (Shannon) — **작은 LM이 쉽게 예측하는(perplexity 낮은) 토큰은 지워도 정보 손실이 작다**

```
원문:  "Sam bought a dozen boxes, each with 30 highlighter pens inside, ..."
압축:  "Sam bought dozen boxes each 30 highlighter pens, ..."   ← 문법은 깨져도 정보는 남는다
```

coarse-to-fine 3단계:

1. **budget controller** — 지시·질문은 살리고(낮은 압축률), 예시들은 통째로 걸러낸다
2. **토큰 단위 반복 압축** — 토큰 간 의존성을 보며 세밀하게 삭제
3. 압축용 작은 LM(Alpaca-7B)과 대상 LLM의 **분포 정렬**

- 하네스 관점: 압축기 = 모델 *밖*의 부품 — 오늘 실습 '간단 압축'의 본격판

<p class="small">출처: LLMLingua (우리 papers/ PDF 기준) §1–4</p>

# LLMLingua — 결과: 20배로 눌러도 버틴다

GSM8K (GPT-3.5-Turbo, few-shot 프롬프트 압축):

| | EM | 토큰 | 압축률 |
|---|---|---|---|
| 원본 프롬프트 | 78.85 | 2,366 | 1x |
| **LLMLingua** | **79.08** | 446 | **5x** |
| **LLMLingua** | **77.33** | 117 | **20x** |
| Selective-Context (나이브 삭제) | 44.20 | 157 | 15x |

- 5x에서는 원본보다 **오히려 높다** — 20x에서도 겨우 −1.52
- 나이브하게 지우면 추론 사슬이 끊긴다: 같은 조건에서 **−33점 이상** 차이
- 지연: 8.6s → **1.3s** (10x 압축 시, 5.7x 가속) — **비용과 지연을 동시에** 절감

# 현장 노트 ② — 프롬프트 캐싱 과금과 시스템 프롬프트 구조화

같은 접두사를 다시 보내면 벤더가 **캐시된 만큼 싸게** 받는다 (Anthropic 기준, 타 벤더 유사):

| | 배율 (입력가 대비) |
|---|---|
| 캐시 **쓰기** (첫 요청) | ~1.25x |
| 캐시 **읽기** (재사용) | **~0.1x** |

- 원리: **접두사(prefix) 일치** — 앞부분이 1바이트만 달라져도 그 뒤 캐시 전부 무효
- → **시스템 프롬프트 구조화**: 변하지 않는 것(역할·규칙·도구)은 **앞**, 변하는 것(날짜·검색 결과·질문)은 **뒤**
- 함정: 시스템 프롬프트에 `datetime.now()` 한 줄 → 적중률 0%
- **긴장 관계**: 트리밍이 히스토리의 *앞*을 건드리면 캐시 전멸 — 지울 때도 접두사 안정성을 계산에 넣어라

<p class="small">출처: Anthropic prompt caching 문서 (배율은 5분 TTL 기준)</p>

# 컨텍스트 실패 모드 3종 — 실제 하네스의 대응

| 실패 | 증상 | 하네스 대응 |
|---|---|---|
| **Poisoning** (오염) | 환각·오류가 컨텍스트에 들어가 계속 재참조된다 | 검증 후 기록 · 오염 구간 잘라내기 |
| **Distraction** (산만) | 대량의 텍스트에 파묻혀 지시를 잊는다 | 선별 + 예산 상한 · 지시를 **끝에** 재주입 |
| **Confusion** (혼동) | 비슷한 도구·문서가 많아 오선택 | 개수 자체를 줄인다 (W3 도구 절벽) |

실제 코딩 에이전트(Claude Code류)의 3종 세트:

1. **관찰 잘라내기** — W3의 `OBS_MAX_CHARS`가 정확히 이것의 미니어처
2. **자동 요약(compaction)** — 예산 임박 시 오래된 히스토리를 요약으로 교체
3. **서브에이전트 격리** — 큰 탐색은 딴 컨텍스트에서 시키고 **결론만** 받아온다 → W11 멀티에이전트의 이유 중 하나

# 🏁 중간 데모 체크포인트 — 단일 에이전트, 완성

오늘 `context.py`가 붙으면 **from-scratch 단일 에이전트의 완성형**이다:

```
W1 두뇌(llm) → W2 숙고(reasoning) → W3 손(tools) → W4 척추(loop)
→ W5 심장(retriever) → W6 손과 심장의 연결(agentic RAG) → W7 전두엽(planner)
→ W8 거울(reflect) → W9 작업기억 관리(context) ✅
```

**오늘 실습 말미 = '내 에이전트 중간 데모'** (1인 3분, 중간 점검을 대신한다):

- 과제: 논문 여러 편에 대한 QA를 **토큰 예산 내에서** 수행
- 보여줄 것: ① 트레이스(W4 어휘로) ② 예산 초과 시 **무엇을 버리는지** ③ 완료 기준 충족
- "잘한다/못한다"는 아직 눈대중 — 정식 채점기는 **W13 평가 하네스**에서 만든다

# 오늘의 세 줄 요약

1. **컨텍스트는 유한 자원, 위치가 성능이다** — U자 곡선: 중간에 둔 정답은 안 준 것(56.1%)만 못하고, 긴 창을 사도 안 고쳐진다
2. **감사 절차: 측정 → 선별 → 정렬 → 압축** — 넣을수록 좋아지는 게 아니라, *고를수록* 좋아진다. 캐싱 때문에라도 고정은 앞, 변동은 뒤
3. **압축은 하네스의 부품이다** — LLMLingua: 20x 압축에 −1.5점, 지연 5.7x 단축. 잘 지우는 것과 막 지우는 것(−33점)은 다른 기술
