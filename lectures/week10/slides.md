# "컨텍스트를 늘리면 되잖아요" — 안 되는 이유 셋

| 이유 | 내용 | 어디서 봤나 |
|---|---|---|
| **끝이 있다** | 관계는 몇 달을 가고, 대화는 결국 창을 넘친다 | W9: 유한 자원 |
| **넣어도 못 쓴다** | 긴 컨텍스트의 중간은 잘 안 보인다 (U자 곡선) | W9: Lost in the Middle |
| **비싸고 느리다** | 매 질문마다 대화 전체(평균 26,000토큰)를 다시 읽는다 | 오늘 Mem0가 측정 |

그래서 방향을 바꾼다:

- **단기 메모리** = 지금 세션의 대화 버퍼 (컨텍스트 안, W9에서 관리법 배움)
- **장기 메모리** = 컨텍스트 **밖**의 외부 저장소 — 쓰고(저장), 찾고(검색), 고친다(갱신)
- 오늘의 설계 질문: **무엇을, 어디에, 어떻게 저장하고 언제 꺼내오는가**

<p class="small">출처: Mem0 논문 (우리 papers/ PDF 기준) §1·§4.1 — LOCOMO 대화 평균 ~26K 토큰</p>

# MemGPT — 운영체제에서 훔쳐온 아이디어

OS의 **가상 메모리**: 물리 RAM은 작지만, 디스크와 페이징하면 앱은 "무한한 메모리"의 환상을 갖는다.

```
        운영체제                      MemGPT
  ┌──────────────┐            ┌──────────────────┐
  │  RAM (빠름·작음) │            │  main context     │ ← 프롬프트 토큰 = 컨텍스트 창
  ├──────────────┤   페이징   ├──────────────────┤
  │  디스크 (크고 느림)│  ⇅        │  external context │ ← 외부 저장소 (DB)
  └──────────────┘            └──────────────────┘
```

- 컨텍스트 창 = **main context** (여기 있는 것만 모델이 볼 수 있다)
- 외부 저장소 = **external context** (보려면 반드시 main으로 **퍼 와야** 한다)
- 페이징을 누가 하나? — **모델 자신이, function call로** (W3 배관의 재사용)

<p class="small">출처: MemGPT 논문 (우리 papers/ PDF 기준) §1–2 · Figure 1</p>

# MemGPT의 메모리 계층 해부

**main context** (프롬프트 토큰) — 세 칸으로 나뉜다:

| 칸 | 성격 | 내용 |
|---|---|---|
| system instructions | 읽기 전용 | 메모리 사용법·함수 스키마 |
| **working context** | 읽기/쓰기 (함수로만) | 사용자·페르소나의 핵심 사실 |
| FIFO queue | 롤링 | 최근 메시지 + 맨 앞에 **재귀 요약** |

**external context** — 두 저장소: **recall storage**(전체 대화 이력) · **archival storage**(임의 문서·노트)

- **queue manager**가 넘침을 관리: 토큰이 경고선(예: 창의 70%)을 넘으면 시스템 메시지로 경고 → 모델이 중요한 것을 working context/archival로 옮길 기회 → 그래도 넘치면 오래된 메시지를 **요약으로 접어서** recall로 퇴거
- W9에서 손으로 하던 트리밍·요약이, 여기서는 **시스템의 상시 정책**이 됐다

<p class="small">출처: MemGPT 논문 (우리 papers/ PDF 기준) §2.1–2.2</p>

# 스스로 페이징하는 모델 — 트레이스로 보기

사용자가 지나가듯 말한 정보를 모델이 **스스로 저장**한다 (개념 트레이스):

```
user:  아 맞다, 다음 달부터는 대전 캠퍼스로 옮겨요.
model: working_context.replace("근무지: 서울" → "근무지: 대전(다음 달~)")
model: "축하드려요! 대전 생활 준비는 잘 되어 가나요?"
--- (몇 주 뒤, 해당 대화는 이미 컨텍스트 밖) ---
user:  내가 어디로 옮긴다고 했었죠?
model: recall_storage.search("근무지 이동")   ← 페이지네이션 검색
model: "다음 달부터 대전 캠퍼스로 옮기신다고 하셨어요."
```

- 저장도 검색도 **function call** — W3에서 만든 배관에 "메모리 함수"를 꽂았을 뿐
- 함수 연쇄(chaining)로 여러 페이지를 이어 읽는다 — 다단계 회수
- 시스템 프롬프트가 메모리 사용법을 가르친다: **메모리 관리도 결국 프롬프트로 위임된 정책**

<p class="small">출처: MemGPT 논문 (우리 papers/ PDF 기준) §2.3 · Figure 3 (트레이스는 수업용 재구성)</p>

# Mem0 — 추출과 갱신, 두 박자 파이프라인

MemGPT가 "모델에게 맡기는 OS"라면, Mem0는 **정해진 파이프라인이 뒤에서 도는** 실전 설계:

```
대화 진행 ─┬─ [추출 단계]  새 메시지 쌍 + 대화 요약(비동기 갱신) + 최근 10개 메시지
           │               → LLM이 '기억할 만한 사실' 후보 ω₁…ωₙ 추출
           └─ [갱신 단계]  후보마다: 의미상 비슷한 기존 기억 top-10 검색
                           → LLM이 tool call로 연산 하나를 선택
                           → ADD / UPDATE / DELETE / NOOP
```

- 저장 단위가 대화 원문이 아니라 **추출된 사실**(자연어 한 줄) — 그래서 작고 검색이 잘 된다
- 요약(전체 맥락) + 최근 창(세부 맥락)을 함께 줘야 추출이 정확하다
- 별도 분류기 없이 **LLM의 판단 + function calling**으로 연산을 고른다 — 또 W3 배관

<p class="small">출처: Mem0 논문 (우리 papers/ PDF 기준) §2.1 · Figure 2 (m=10, s=10, GPT-4o-mini)</p>

# 갱신이 왜 어려운가 — 모순 해소 예시 3개

새 사실이 왔을 때, 그냥 쌓으면 안 된다. 기존 기억과 **대조**해야 한다:

| 새로 추출된 사실 | 기존 기억 | 연산 |
|---|---|---|
| "대학원에서 GNN을 연구한다" | (없음) | **ADD** |
| "아침엔 라떼만 마신다" | "커피를 좋아한다" | **UPDATE** (보강) |
| "지난달 대전으로 이사했다" | "서울에 산다" | **DELETE** 후 ADD (모순) |
| "저 GNN 연구한다니까요" | "GNN을 연구한다" | **NOOP** (중복) |

- 무지성 append의 말로: "서울에 산다"와 "대전에 산다"가 **둘 다 검색되는** 메모리
- 갱신 연산은 사실상 **버전 관리** — 무엇이 최신 참인지를 저장소가 책임진다
- W9의 컨텍스트 오염(poisoning)이 메모리에서는 **영구 오염**이 된다 — 그래서 더 무겁게 다룬다

<p class="small">출처: Mem0 논문 (우리 papers/ PDF 기준) §2.1 — 연산 4종, 예시는 수업용 재구성</p>

# 장기 메모리 검색 = W5 retriever의 재등장

Mem0의 검색(갱신 때도, 답변 때도)은 우리가 이미 만든 그 부품이다:

| | W5 `retriever.py` | W10 장기 메모리 검색 |
|---|---|---|
| 저장물 | 문서 청크 | 추출된 사실 (한 줄 기억) |
| 색인 | 임베딩 → 벡터 저장소 | 임베딩 → 벡터 저장소 |
| 질의 | 사용자 질문 | 사용자 질문 *또는* 새 후보 사실 |
| 회수 | top-k 유사도 | top-k 유사도 |

- **같은 부품, 다른 데이터** — 문서 대신 *나의 과거*를 색인한다
- 그래서 오늘 실습이 가볍다: `retriever.py`를 알면 `memory.py`의 절반은 이미 안다
- RAG와의 차이는 검색이 아니라 **쓰기 경로**(추출·갱신)에 있다 — RAG 문서는 스스로 안 변한다

# Mem0 — 숫자: full-context와의 정면 비교

LOCOMO 벤치마크 (다세션 대화, 평균 ~26K 토큰), LLM-as-a-Judge 점수 **J**:

| 방법 | J (전체) | 총 지연 p95 | 저장/입력 토큰 |
|---|---|---|---|
| full-context (대화 전체 주입) | **~73%** | 17.1초 | ~26K/질문 |
| 최고 RAG 설정 | ~61% | — | 청크 회수 |
| **Mem0** | ~67% | **1.44초 (92%↓)** | 기억 저장 ~7K/대화 |
| Mem0ᵍ (그래프 메모리) | 68.4% | 2.59초 (85%↓) | ~14K/대화 |

- **p95 지연 91% 감소 · 토큰 비용 90% 이상 절감** (vs full-context) — 검색 지연은 p50 0.148초
- **소금 한 줌:** 정확도만 보면 full-context가 아직 1등이다 — 메모리는 정확도를 사는 기술이 아니라, **거의 같은 품질을 1/10 비용·지연에 사는** 기술. 그리고 대화가 길어질수록 full-context 쪽 비용은 계속 자란다
- 채점자가 또 LLM이다(J) — W13에서 정면으로 다룰 그 문제

# 무엇을 꺼내오나 — 최신성 × 중요도 × 관련성

Generative Agents(2023)가 남긴 유산 — 메모리 검색 점수의 고전 공식:

```
score(기억) = α·recency + β·importance + γ·relevance   (각각 [0,1] 정규화)
```

| 축 | 구현 | 직관 |
|---|---|---|
| **recency** | 마지막 접근 후 지수 감쇠 (감쇠율 0.995) | 방금 일은 아직 머릿속에 있다 |
| **importance** | LLM이 1–10점 채점 ("아침 식사"=낮음, "이별"=높음) | 시시한 기억은 밀려난다 |
| **relevance** | 질의와의 코사인 유사도 | W5의 그 수식, 세 번째 재사용 |

- 관련성 하나로는 부족하다 — 오래되고 사소한 기억이 우연히 비슷할 수 있다
- 역으로 읽으면 **망각 정책**이 된다: 점수가 계속 낮은 기억 = 지워도 되는 기억

<p class="small">출처: Generative Agents 논문 (우리 papers/ PDF 기준) §4.1 — retrieval function</p>

# 현장 노트 ① — 메모리 계층과 스키마

실무 시스템은 기억을 한 통에 넣지 않는다. **수명(scope)으로 3계층**:

| 계층 | 수명 | 예 | 우리 코드에선 |
|---|---|---|---|
| **세션 메모리** | 대화 하나 | 지금 다루는 논문, 방금의 지시 | 대화 버퍼 (W9 관리) |
| **유저 메모리** | 사용자 계정 | 이름·연구 주제·선호 (Mem0의 주 무대) | `memory.json` |
| **영구/조직 메모리** | 서비스 전체 | 도메인 지식, 팀 규약 | W5 문서 인덱스에 가깝다 |

**메모리 스키마** — 기억 한 줄에도 최소한의 구조를:

```json
{"content": "연구 주제는 GNN", "type": "preference",
 "created_at": "...", "last_accessed": "...", "source": "session-042"}
```

- `type`(사실/선호/사건)에 따라 갱신 규칙이 다르다 — 선호는 UPDATE, 사건은 append
- `source`를 남겨야 나중에 **"이 기억 어디서 왔지?"**를 추적할 수 있다 (감사 가능성)

# 현장 노트 ② — 저장 결정 절차 · 망각 · PII

**무엇을 저장하나 — 결정 절차** (Mem0 파이프라인의 일반형):

```
① 추출     이 발화에 다음 세션에도 유효한 사실이 있는가? (없으면 끝)
② 대조     비슷한 기존 기억 검색 → 중복인가? 모순인가?
③ 갱신     ADD / UPDATE / DELETE / NOOP 중 하나 — 무지성 append 금지
```

**TTL·망각 정책** — 안 지우는 메모리는 쓰레기장이 된다:
- 계층별 TTL(세션=대화 끝, 유저=갱신형, 캐시성=만료일) + 점수 기반 정리(낮은 recency×importance부터)
- 삭제 대신 **무효화 마킹**도 선택지 — 시간 추론("예전엔 서울 살았었지")이 필요하면

**PII 처리** — 메모리는 개인정보 저장소가 되기 쉽다:
- 저장 **전** 필터링이 원칙 (주민번호·카드번호·건강정보는 애초에 추출 금지 목록으로)
- "내 정보 지워줘"가 동작해야 한다 — 삭제 API 없는 메모리는 규제(GDPR류) 앞에서 부채
- ⚠️ 복선: 메모리에 거짓을 **심는** 공격(메모리 오염)이 가능하다 — W14 보안에서 정면으로
