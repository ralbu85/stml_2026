# 한 번 삐끗하면 끝까지 간다

W4 루프가 W5–6에서 만든 검색 도구로 2단계 멀티홉 질문을 처리한 실패 트레이스:

```
Thought: "2023년 그 논문"을 검색하자
Action: search("2023 논문")            ← 첫 검색어부터 잘못 골랐다
Observation: (관련 없는 결과 10건)
Thought: 이 결과로 보아…               ← 오염된 문맥 위에서 계속 전진
  …                                     ← 뒤로 돌아가는 수단이 없다
```

- ReAct는 **greedy**: 매 스텝 "지금 최선"만 — 대안 비교도, 백트래킹도 없다
- 우리는 이미 두 가지 부분 처방을 봤다:
  - W2 self-consistency — 경로 N개를 **병렬로** 뽑아 다수결 (도중 개입은 없음)
  - W3 DFSDT — 실패하면 **물러나는** 탐색 (ReAct 35.3 → 63.8)
- 오늘은 이 계보의 완성형: **분기하고, 평가하고, 물러나는** 탐색을 일반화한다

# 처방 ①: 과제 분해 (task decomposition)

복잡한 질문은 통째로 풀지 말고 **하위 단계로 나눈다**:

```
Q: "ReAct 논문 1저자의 소속 대학이 있는 도시의 인구는?"

계획:
  1. ReAct 논문 1저자 찾기
  2. 그 사람의 소속 대학 찾기        ← 1의 결과에 의존
  3. 그 대학이 있는 도시 찾기        ← 2의 결과에 의존
  4. 그 도시의 인구 검색             ← 3의 결과에 의존
```

- 각 단계는 모델이 **한 번에 풀 수 있는 크기** — 분해가 곧 난이도 조절
- 단계 사이의 **의존 관계**가 드러난다 → 실행 순서·병렬 가능성이 보인다
- 오후 실습 `planner.py`가 정확히 이것: 질문 → 단계 리스트 → 순차 실행

# 처방 ②: 계획을 언제 세우나 — 두 유파

| | **Interleaved** (ReAct, W4) | **Plan-and-execute** (오늘) |
|---|---|---|
| 방식 | 한 스텝마다 생각→행동→관찰 | **계획을 먼저 다 짜고** → 실행 |
| 계획 수정 | 매 스텝 암묵적으로 | 실행 후 명시적 재계획(replan) |
| 관찰 반영 | 즉시 (유연) | 계획 시점엔 관찰 없음 (경직) |
| LLM 호출 | 스텝마다 (많음) | 계획 1회 + 실행 (적음) |
| 맞는 과제 | 예측 불가·탐색적 과제 | 구조가 뻔한 다단계 과제 |

- 정답이 있는 이분법이 아니다 — **과제의 예측 가능성**이 가르는 축
- "미리 다 짜면 싸고 빠르다, 대신 계획이 틀리면?" → 이 긴장이 오늘 후반부(ReWOO) 전체

# 현장 노트 ① — plan–execute–replan 루프와 DAG

실무 프레임워크(LangChain 등)의 **plan-and-execute 에이전트** 표준형:

```
계획(plan) → 한 단계 실행(execute) → 남은 계획 재검토(replan)
                                        ├ 그대로 진행
                                        ├ 계획 수정 (단계 추가·삭제)
                                        └ 조기 종료 (이미 답이 나옴)
```

- **replanning**: 계획은 세우는 것보다 **고치는 게** 본체 — 관찰이 들어올 때마다 갱신
- 서브태스크 분해의 실제 자료구조는 리스트가 아니라 **DAG** (방향 비순환 그래프):
  의존 없는 단계는 **병렬 실행**, 의존 있는 단계만 순서 보장
- 계획은 자연어 문장이 아니라 **파싱 가능한 구조**로 뽑는다 (JSON 리스트 등) — 실습에서 체감

DAG는 아까 분해 슬라이드의 의존 화살표를 다시 가리키며 — "화살표 없는 단계끼리는 동시에 돌려도 된다, 이게 곧 지연 절감."

# 현장 노트 ② — 계획 검토 게이트 (human-in-the-loop)

계획을 먼저 뽑는 구조의 숨은 보너스: **실행 전에 계획을 검토할 수 있다**

```
질문 → [계획 생성] → ★ 검토 게이트 ★ → [실행]
                       ├ 사람 승인 (고위험 단계)
                       └ 검증기 통과 (형식·권한·예산 체크)
```

- ReAct는 행동이 **하나씩 즉석에서** 나온다 — 미리 보여줄 계획 자체가 없다
- 승인 지점(approval point)을 두는 기준: **비가역 행동** 앞 — 메일 발송, 결제, 파일 삭제
  (W3 멱등성 논의의 연장: "재시도하면 되지"가 안 통하는 그 도구들)
- 게이트는 사람만이 아니다 — 규칙 검증기, 예산 상한, 도구 화이트리스트도 같은 자리에

> 계획의 가치는 성능만이 아니라 **통제 가능성**이다 — W14 보안에서 이 게이트가 방어선으로 재등장

# Game of 24 — CoT는 왜 4%인가

숫자 4개와 사칙연산으로 24 만들기: `4 9 10 13` → `(13-9)*(10-4)=24`

```
CoT (한 줄로 전진):     4+9=13 → …        ← 첫 수가 틀리면 그대로 끝
                        └ CoT 실패 샘플의 약 60%가 첫 단계에서 이미 탈락

ToT (트리로 탐색):          [4 9 10 13]
                    ┌──────────┼──────────┐
                 13-9=4     10-4=6      4+9=13
                (남은 4,4,10) (남은 6,9,13) (남은 10,13,13)
                  maybe       sure ✓      impossible ✗
```

- 3수만 내다보면 되는 문제인데도, **왼쪽에서 오른쪽으로만 쓰는** 생성은 첫 수를 무르지 못한다
- ToT: 후보를 **여럿 만들고**, 가망을 **평가하고**, 가망 없는 가지는 **버린다**

# ToT의 3요소 — 생성기 · 평가기 · 탐색

ToT는 문제 풀이를 **트리 탐색**으로 다시 정의한다 (노드 = 부분 해):

| 요소 | 질문 | Game of 24에서 |
|---|---|---|
| **생성기** G | 다음 생각 후보를 어떻게 여럿 뽑나? | "가능한 다음 수식" 제안 프롬프트 |
| **평가기** V | 어느 가지가 유망한지 어떻게 아나? | **LLM 스스로** sure / maybe / impossible 분류 |
| **탐색** | 트리를 어떤 순서로 도나? | BFS, 단계마다 상위 **b=5**개만 유지 |

- 평가기가 급소: 정답을 몰라도 **"가망 없음"은 판정 가능** ("남은 수가 너무 크다")
  — 생성하는 모델과 평가하는 모델이 같아도 작동한다
- 탐색은 고전 AI의 BFS/DFS 그대로 — 새로운 건 **휴리스틱 함수 자리에 LLM**이 들어간 것

평가기 직관: 24 만들기의 정답 경로는 몰라도 '10과 13만 남았는데 24가 되나?'는 즉답 가능. 생성보다 검증이 쉽다는 비대칭이 ToT의 지렛대.

# ToT 결과 — 4% → 74%

Game of 24, GPT-4, 100문제 성공률:

| IO | CoT | CoT-SC (k=100) | **ToT (b=1)** | **ToT (b=5)** |
|---|---|---|---|---|
| 7.3% | 4.0% | 9.0% | 45% | **74%** |

- CoT를 **100번 뽑아 최선을 골라도 49%** — 독립 시도 100번 < 가지치기 있는 탐색 1번
- b=1(가지 1개)만으로도 45% — 이득의 몸통은 폭이 아니라 **평가·백트래킹 구조** 그 자체
- 모델은 그대로, 하네스만 바꿔 4→74 — "하네스가 성능이다" 테제의 증거가 또 쌓인다

# ToT의 값 — 탐색은 공짜가 아니다

같은 Game of 24, 문제당 비용:

| | 생성 토큰 | 문제당 비용 | 성공률 |
|---|---|---|---|
| IO (best of 100) | 1.8k | $0.13 | 33% |
| CoT (best of 100) | 6.7k | $0.47 | 49% |
| **ToT (b=5)** | 5.5k | **$0.74** | **74%** |

- CoT 대비 문제당 **수 배의 비용·지연** — 노드마다 생성·평가 호출이 붙는다
- 논문 스스로의 권고: 쉬운 과제엔 쓰지 마라 — **탐색·계획이 필요한 과제**용 도구
- 토론 예고: *탐색 비용 대비 성능 이득은 언제 정당한가?* — 여러분의 과제로 답해보라

# ReWOO — Planner · Worker · Solver

관찰(도구 결과)을 기다리지 않고 **계획을 먼저 끝까지 쓴다**:

```
Planner (LLM 1회):  Plan1: ReAct 1저자 검색      → #E1 = search(…)
                    Plan2: #E1의 소속 대학 검색   → #E2 = search(#E1 …)
                    Plan3: #E2 도시의 인구 검색   → #E3 = search(#E2 …)
Worker  (LLM 아님):  #E1, #E2, #E3 를 도구로 실제 채운다
Solver  (LLM 1회):  계획 + 증거 전부를 받아 최종 답 작성
```

- 급소는 **변수 참조 `#E`**: 아직 없는 관찰 자리를 변수로 비워두고 계획을 잇는다
  — 관찰 없이도 다단계 의존 계획이 가능한 이유
- 아까 본 plan-and-execute 유파의 정제된 논문 버전 — 분해(계획) / 실행 / 종합을 **모듈로** 분리

# 왜 싸지나 — 프롬프트 반복의 제거

ReAct의 숨은 비용: 매 스텝, **지금까지의 전부**를 다시 보낸다

| | ReAct (interleaved) | ReWOO (plan-first) |
|---|---|---|
| LLM 호출 | 스텝 수만큼 (n회) | **2회** (Planner + Solver) |
| 매 호출의 입력 | 시스템 프롬프트+도구 스키마+**누적 이력 전부** | 계획 1회분 / 종합 1회분 |
| 토큰 증가 | 스텝에 따라 **제곱급** 누적 | 선형 |
| 관찰이 계획을 바꾸나 | 매 스텝 가능 | 불가 (계획은 고정) |

- 같은 다단계 질문에서 중복 재전송이 사라진다 — 아낀 것은 성능이 아니라 **토큰과 왕복**
- W3에서 본 "도구 n번 = 왕복 n+1번" 문제의 정면 처방
- 대가는 마지막 줄: 관찰이 계획을 못 고친다 → 결과 다음 슬라이드에서 청구서 확인

# ReWOO 결과 — 64% 싸게, 4.4점 더

gpt-3.5-turbo, 공개 벤치마크 6종 평균: 토큰 **64% 절감** + 정확도 **+4.4%p**

| HotpotQA (multi-hop QA) | 정확도 | 질문당 토큰 | 1k질문 비용 |
|---|---|---|---|
| ReAct | 40.8 | 9,795 | $19.59 |
| **ReWOO** | **42.4** | **1,986 (≈1/5)** | **$3.97** |

- 모든 도구가 고장 나면("No evidence found") — ReAct **−40.8 (전멸)** vs ReWOO −29.2:
  계획이 살아 있으면 Solver가 자체 지식으로 일부를 건진다
- **소금 한 줌:** 계획이 처음부터 틀리면? 관찰을 반영할 길이 없다 — replanning이 없는 구조.
  그리고 도구를 5→7개로 늘리자 성능 하락 (실패 20건 중 17건이 도구 오선택 — W3 도구 절벽 재확인)

# 오늘의 세 줄 요약

1. **ReAct는 greedy** — 잘못 든 길을 무를 구조가 없다. 처방 = 분해·계획·탐색
2. **ToT** — 생성기·평가기·탐색으로 생각을 트리로: Game of 24 CoT 4% → **74%** (단, 비용 수 배)
3. **ReWOO** — 계획을 관찰과 분리(#E 변수): 토큰 **64% 절감** + 정확도 +4.4%p, 대신 replanning 없음

**다음 주 (W8. 자기반성):**
계획을 세워도 첫 시도는 틀린다 — 실패를 언어 피드백으로 요약해 재시도하는 구조를 배운다 (Reflexion · Self-Refine).
