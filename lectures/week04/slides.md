# W2 실습, 우리 루프의 마지막 장면

```
Thought: 계산기가 필요하다.
Action: {"tool": "calculator", "input": "1400*0.29"}
Observation: (아직 'calculator' 도구가 없습니다. 아는 범위에서 답하세요.)
```

- 루프(하네스)는 완성했다 — **손이 없을 뿐**
- 모델은 이미 도구를 *부르려고* 한다. 오늘 그 빈자리를 채운다
- 이론: 이 배관이 실제 API에서 어떻게 생겼나 → 오후: `tools.py`로 직접

# 말만 하는 모델

일반 모델에 곱셈 하나를 물으면:

```
Q: 3847 × 2963 = ?
A: 11,398,261     ← 그럴듯하다. 그리고 틀렸다 (정답 11,398,661)
```

- 모델은 **계산하지 않는다** — *계산처럼 보이는 텍스트*를 생성한다
- 자릿수가 늘수록 "그럴듯함"과 "맞음"의 거리가 벌어진다

# 언어 모델의 세 가지 결핍

| 결핍 | 예 | 필요한 것 |
|---|---|---|
| **계산** | 산수, 날짜 연산, 단위 변환 | 계산기·코드 실행 |
| **지식의 시효** | 어제 뉴스, 우리 회사 문서 | 검색·DB 조회 |
| **부작용** | 메일 발송, 파일 쓰기, 예약 | 실행 권한 있는 함수 |

- 셋 다 **파라미터 안에 없는 것들** — 더 큰 모델로도 해결되지 않는다
- W1 해부도의 세 번째 부품 **Tools** = 이 결핍을 밖에서 채우는 통로
- 도구는 에이전트가 **세계와 만나는 유일한 접점**이다

# 5–17′ · Function Calling 내부

---

# 큰 그림: 다섯 단계 파이프라인

```
① 알리기   하네스 → 모델   "이런 도구들이 있다" (JSON Schema)
② 의도     모델 → 하네스   "calculator를 이 인자로 불러 달라" (JSON)
③ 파싱     하네스           JSON을 읽어 어느 함수인지 결정
④ 실행     하네스           진짜 함수 호출 — 파이썬이 실행한다
⑤ 재주입   하네스 → 모델   결과를 대화에 붙여 다시 묻는다
```

- 모델이 하는 일은 **②뿐** — 나머지 넷은 전부 우리 코드(하네스)
- 그래서 *"모델은 실행하지 않는다, JSON을 쓸 뿐"*
- W2의 `parse_step()`이 ③, `dispatch()`가 ④, Observation 재주입이 ⑤였다

<!--

"오늘 새로 배우는 건 ①(스키마)과, 이걸 공식 API가 어떻게 표준화했는가다."

# ① 알리기 — 도구 스키마 (요청 JSON)

실제 API 요청에 도구를 이렇게 실어 보낸다 (OpenAI 계열·aisuite 동일):

```json
{
  "model": "openai:gpt-4o-mini",
  "messages": [{"role": "user", "content": "1400의 29%는?"}],
  "tools": [{
    "type": "function",
    "function": {
      "name": "calculator",
      "description": "산술식을 계산한다. 수식 계산이 필요할 때만 사용.",
      "parameters": {
        "type": "object",
        "properties": {"expression": {"type": "string",
                        "description": "예: '1400*0.29'"}},
        "required": ["expression"]
      }
    }
  }]
}
```

<!--
[7분] 화면에 실제 JSON. "parameters가 JSON Schema라는 표준 형식 — 폼 검증에 쓰는 그 스키마다."
description이 두 군데(함수·인자) 있다는 걸 짚어두기 — 17분 구간(도구 정의 = 프롬프트)의 복선.

# ② 의도 — 모델의 응답 JSON

```json
{
  "choices": [{
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "calculator",
          "arguments": "{\"expression\": \"1400*0.29\"}"
        }
      }]
    }
  }]
}
```

- `content`가 비고 `tool_calls`가 온다 — **답이 아니라 부탁**
- 함정: `arguments`는 객체가 아니라 **문자열** — 한 번 더 `json.loads()` 해야 한다
- 이 문자열이 깨진 JSON일 수도 있다 → 실패 모드 (17분 구간)

<!--
[9분] "모델의 출력이 곧 함수 호출처럼 보이지만, 실제로는 '이렇게 불러줘'라는 텍스트다."
arguments 이중 인코딩 함정은 실습에서 전원이 한 번씩 밟는 지뢰 — 미리 짚는다.
-->

# ③④⑤ — 실행과 재주입 (전부 우리 코드)

```python
call = response.choices[0].message.tool_calls[0]
args = json.loads(call.function.arguments)        # ③ 파싱
result = my_tools[call.function.name](**args)     # ④ 실행 ← 파이썬이 한다

messages.append(response.choices[0].message)       # 모델의 '부탁'을 이력에
messages.append({"role": "tool",                   # ⑤ 결과 재주입
                 "tool_call_id": call.id,
                 "content": str(result)})
second = client.chat.completions.create(model=..., messages=messages)
# → "1400의 29%는 406입니다."  (이제야 최종 답)
```

- 새 role **`tool`** — W1에서 배운 system/user/assistant의 네 번째 형제
- 도구 1회 사용 = **API 왕복 2번** (부탁 1번 + 최종 답 1번). 비용·지연도 2배

# 우리 수제 버전 vs 공식 API

W2에 우리가 만든 것이 정확히 이것의 **수제 버전**이다:

| | 우리 `loop.py` (W2) | 공식 function calling |
|---|---|---|
| 도구 알리기 | 시스템 프롬프트에 텍스트로 | `tools=[...]` 스키마 |
| 호출 의도 | `Action: {...}` 텍스트를 정규식 파싱 | `tool_calls` 구조화 필드 |
| 형식 보장 | 없음 — 깨지면 "형식 오류" 재시도 | 서버가 **문법 제약 디코딩**으로 보장 |
| 결과 재주입 | `Observation:` user 메시지 | `role: "tool"` 메시지 |

- 원리는 동일 — API는 ②③의 **파싱 실패율을 서버가 줄여주는 것**
- 수제로 먼저 만든 이유: 배관이 보이면 디버깅이 보인다 (프레임워크는 W10)

문법 제약 디코딩은 한 줄만: "출력 토큰을 스키마에 맞는 것만 뽑게 강제하는 것."

# 현장 노트 ① — 도구 정의가 곧 프롬프트다

모델이 도구에 대해 아는 것은 **스키마의 문자열이 전부**다. 그래서:

**좋은 도구 정의 체크리스트**
1. **이름은 동사형·구체적** — `search_docs` (○) / `helper2` (×)
2. **설명에 "언제 쓰나"와 "언제 안 쓰나"를 둘 다** — "문서 내용 질문에 사용. 일반 상식에는 사용하지 말 것."
3. **인자에 예시와 제약** — "ISO 날짜, 예: 2026-09-01"
4. **에러 메시지도 모델이 읽는다** — "실패"(×) / "날짜 형식 오류. YYYY-MM-DD로 다시."(○)

> 도구 문서화 = 프롬프트 엔지니어링. 사람이 아니라 **모델이 읽는 문서**를 쓰는 것.

<!--

4번이 실무자들도 자주 놓치는 것 — "에러 메시지가 다음 턴의 프롬프트가 된다."
-->

# 현장 노트 ② — 실패 모드 4종과 대응 원칙

| 실패 | 예 | 대응 |
|---|---|---|
| 없는 도구 호출 | `"tool": "calculater"` (오타) | 가용 도구 목록을 **관찰로** 돌려준다 |
| 깨진·틀린 인자 | 닫히지 않은 JSON, 타입 불일치 | 무엇이 틀렸는지 관찰로 |
| 실행 에러 | 0으로 나누기, 파일 없음 | 예외를 잡아 **문자열로** |
| 응답 없음 | 외부 API 지연 | **타임아웃** 걸고 관찰로 |

**대원칙: 에러도 Observation이다** — 도구가 무슨 짓을 해도 루프는 죽지 않는다.
모델이 에러를 *읽고* 다음 수(재시도·다른 도구·포기)를 정하게 한다.

+ 재시도 전 질문 하나: 이 도구는 **멱등**한가? (검색 2번 = 안전 / 메일 발송 2번 = 사고)

멱등성은 예시로만: "'재시도하면 되지'가 통하는 도구와 아닌 도구를 구분하는 게 실무 감각."

# 현장 노트 ③ — 알아두면 좋은 API 스위치

| 스위치 | 하는 일 | 언제 |
|---|---|---|
| `tool_choice` | `auto`(기본) / `required` / 특정 도구 강제 | "반드시 검색부터 해" 같은 강제 |
| 병렬 도구 호출 | 한 응답에 `tool_calls` 여러 개 | 독립적인 조회 여러 건을 한 왕복에 |
| structured outputs (`strict`) | 스키마 **100% 준수**를 서버가 보장 | 인자 파싱 실패를 원천 차단 |

- 병렬 호출은 공짜 점심이 아니다 — 순서 의존 작업(조회→그 결과로 예약)엔 못 쓴다
- 이름은 벤더마다 다르지만 개념 셋(강제·병렬·보장)은 공통

# Toolformer — 스스로 다는 주석

핵심 아이디어: 모델이 **자기 훈련 데이터에 API 호출을 끼워 넣고**, 도움이 된 것만 남겨 다시 학습한다.

```
원문:   "Out of 1400 participants, 400 passed the test."
증강:   "Out of 1400 participants, 400 [Calculator(400/1400) → 0.29]
         passed the test."
```

3단계: ① LM이 호출 후보 위치·내용을 샘플링 → ② 실제로 실행 →
③ **필터: 그 호출이 다음 토큰 예측 손실을 줄일 때만 유지** (L⁻−L⁺ ≥ τ)

- 사람 라벨 0개 — 지난주(W3) STaR의 필터("답 맞으면 남긴다")와 같은 계보:
  **자기 생성 + 유용성 필터**. 보상이 아니라 *손실 감소*가 기준일 뿐

<p class="small">출처: Toolformer 논문 (우리 papers/ PDF 기준) Figure 1·§2</p>

# Toolformer — 결과와 한계

수학 문제(ASDiv), GPT-J **6.7B** 기준:

| GPT-J 원본 | + Toolformer | GPT-3 **175B** |
|---|---|---|
| 7.5 | **40.4** | 14.0 |

- **26배 작은 모델이 GPT-3를 이긴다** — 계산기 사용률 97.9%

# ToolLLM — 16,464개 실제 API의 세계

RapidAPI 실서비스 API 53,190개를 긁어 **16,464개**(49개 카테고리)로 정제 → 도구가 *많아지면* 문제가 바뀐다:

| 도구 5개 (Toolformer) | 도구 16,464개 (ToolLLM) |
|---|---|
| 어떻게 부르나 | **무엇을 고르나** (검색이 필요) |
| 한 번 부르면 끝 | 여러 API 조합, **실패하면 물러나야** |

- 해법 ①: API **retriever** — 도구 자체를 검색해서 후보만 컨텍스트에
- 해법 ②: 탐색 구조를 바꾼다 → **DFSDT** (다음 슬라이드)
- ChatGPT로 실행 트레이스를 만들어 LLaMA-2 **7B**를 SFT → ToolLLaMA

# DFSDT — 실패하면 물러나는 탐색

ReAct의 약점: **한 길로만 간다.** API가 죽거나 잘못 골랐으면 그대로 추락.

```
ReAct:   호출1 → 호출2 → (실패) → 끝.
DFSDT:   호출1 → 호출2 → (실패) → 물러나서 → 호출2' → 성공
                          └ 깊이 우선 트리 탐색 (Depth-First Search Decision Tree)
```

같은 백본에서 추론 전략만 바꿨을 때 (ToolBench 평균 pass rate):

| ReAct | ReAct@N (실패 시 처음부터 재시도) | **DFSDT** |
|---|---|---|
| 35.3 | 44.5 | **63.8** |

- 처음부터 다시(@N)보다 **실패 지점에서 물러나기**가 훨씬 낫다
- 다음 주(W5) 예고: 이 트리를 일반화한 것이 Tree of Thoughts

# ToolLLM — 결과, 그리고 소금 한 줌

| 모델 | pass rate (평균) |
|---|---|
| ChatGPT + DFSDT | 64.8 |
| **ToolLLaMA (7B) + DFSDT** | **66.7** |
| ToolLLaMA + API retriever | 67.3 |

# 토론 예고 — 도구 절벽 (tool cliff)

> 도구가 많아질수록 에이전트는 좋아지는가?

- 스키마도 **컨텍스트를 먹는다** — 도구 100개면 프롬프트가 스키마로 가득
- 비슷한 도구가 많을수록 **오선택**이 늘어난다
- ToolLLM의 답: 도구를 검색하라. 다른 답: 도구를 **줄여라** (좋은 도구 5개 > 어중간한 50개)
