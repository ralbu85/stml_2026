# 모델의 세 가지 결핍

지난주까지 모델은 생각을 잘하게 됐다. 그런데 여전히:

| 결핍 | 예 | 밖에서 채울 것 |
|---|---|---|
| **계산 못 함** | 산수·날짜·단위 | 계산기·코드 실행 |
| **지식의 시효** | 어제 뉴스, 우리 문서 | 검색·DB 조회 |
| **부작용 불가** | 메일·파일·예약 | 실행 권한 있는 함수 |

- W1 해부도의 세 번째 부품 **Tools** = 이 결핍을 밖에서 채우는 통로
- **도구는 에이전트가 세계와 만나는 유일한 접점**이다

# 5–17′ · 함수 호출의 원리

---

# 핵심 개념 — 모델은 실행하지 않는다

"도구를 쓴다"는 말은 오해를 부른다. 실제로 벌어지는 일은 **역할 분담**이다:

```
① 알리기   하네스 → 모델   "이런 도구들이 있다"
② 요청     모델 → 하네스   "calculator를 이 인자로 불러 달라"
③ 파싱     하네스           어느 함수인지 읽어낸다
④ 실행     하네스           진짜 함수를 부른다 (여기서만 실제 계산)
⑤ 재주입   하네스 → 모델   결과를 대화에 붙여 다시 묻는다
```

모델이 하는 일은 **②뿐** — 나머지 넷은 전부 우리 코드(하네스)다.
그래서 *"모델은 실행하지 않고, 실행해 달라고 요청만 한다."*

<!--
[7분] 오늘 이론의 뼈대. 다섯 단계 중 새로 배우는 건 ①(도구를 어떻게 알리나)과 ②③(요청을 어떻게 주고받나)뿐 —
④⑤는 우리가 W2 루프에서 이미 만든 것(dispatch·Observation 재주입)이다. "이미 절반은 만들었다."

# 지난주 우리 것 = 공식 방식의 수제 버전

W2에서 만든 루프가 정확히 이 파이프라인의 **수제 버전**이다. 공식 함수 호출(function calling)과 원리가 같다:

| 단계 | 우리 수제 방식 (W2) | 공식 function calling |
|---|---|---|
| 알리기 | 시스템 프롬프트에 텍스트로 | 도구 **스키마**(JSON Schema) |
| 요청 | `Action:` 텍스트를 파싱 | 구조화된 **tool call** 필드 |
| 형식 보장 | 없음 (깨지면 재시도) | 서버가 형식을 강제 |
| 재주입 | `Observation:` 메시지 | 전용 **`tool` 역할** 메시지 |

- 차이는 **형식을 누가 보장하느냐**뿐 — 공식 API는 파싱 실패를 서버가 줄여준다
- 요청/응답의 실제 JSON 생김새는 **오후 실습에서 직접 보고 만든다**

<p class="small">공식 스키마 형식·필드는 실습 스캐폴드와 API 문서에서 확인 — 이론에선 '원리가 같다'만 남긴다</p>

<!--
[11분] JSON을 화면 가득 띄우지 않는다. 개념은 "역할이 하나 늘었다(tool)"와 "형식 보장을 서버가 대신한다"뿐.
디테일(arguments가 문자열이라 한 번 더 파싱 등)은 실습에서 몸으로 배운다.
-->

---

# 도구 한 번 = 왕복 두 번

파이프라인의 숨은 비용: 도구를 한 번 쓰면 모델을 **두 번** 부른다 — 요청받는 호출 1번 + 결과를 보고 답하는 호출 1번.

- 도구를 n번 쓰면 왕복 n+1번 → **비용·지연이 누적**된다
- 관찰 결과가 길면 **컨텍스트를 먹는다** → W9(컨텍스트) 문제의 씨앗

> 도구는 공짜가 아니다. "이 단계에 정말 도구가 필요한가"를 매번 묻는 감각이 하네스 설계다.

# 17–25′ · 좋은 도구의 조건

---

# 도구 정의가 곧 프롬프트다

모델이 도구에 대해 아는 것은 **정의에 적힌 문장이 전부**다. 그래서 도구를 정의하는 일은 곧 프롬프트를 쓰는 일이다:

- **이름**은 하는 일을 그대로 — `search_docs`(○) / `helper2`(×)
- **설명**엔 "언제 쓰나"뿐 아니라 **"언제 쓰지 마라"** 까지 — 안 그러면 엉뚱한 데 부른다
- **인자**엔 예시와 제약을 — "ISO 날짜, 예: 2026-09-01"
- **에러 메시지**도 모델이 읽는다 — "실패"(×) / "날짜 형식 오류, YYYY-MM-DD"(○)

> 사람이 아니라 **모델이 읽는 문서**를 쓰는 것 — 이것이 도구 설계의 핵심이다.

<!--

---

# 실패는 정상이다 — 에러도 관찰이다

도구는 반드시 실패한다: 없는 도구를 부르고, 인자가 깨지고, 실행 중 에러가 나고, 외부 API가 멈춘다.

**대원칙:** 이 모든 실패를 **관찰(Observation)로 바꿔 모델에게 돌려준다.** 예외로 루프를 죽이지 않는다.

- 없는 도구 → 가용 목록을 관찰로 · 깨진 인자 → 무엇이 틀렸는지 관찰로
- 실행 에러 → 예외를 문자열로 · 무응답 → **타임아웃** 걸고 관찰로
- 그러면 모델이 에러를 *읽고* 다음 수(재시도·다른 도구·포기)를 스스로 정한다

한 가지 더: 재시도해도 안전한가? — **멱등성(idempotency).** 검색 두 번은 안전, 메일 발송 두 번은 사고다.

# 25–33′ · 도구를 배울 수 있나

---

# 여기까지는 "시키는" 방법이었다

스키마·설명·프롬프트 — 전부 사람이 도구 사용법을 **써 넣는** 접근이다. 다른 길: 모델이 도구 쓰는 법을 **스스로 배울** 순 없나?

오늘 발표 2편이 이 질문의 양 극단이다:

| | Toolformer (2023) | ToolLLM (2024) |
|---|---|---|
| 질문 | 도구 쓸 *자리*를 스스로 배울 수 있나? | *수만 개* 실제 API에서는? |
| 규모 | 도구 **몇 개** | 도구 **수만 개** |
| 접근 | 자기 라벨링 + 유용성 필터 | 대규모 API + 탐색 |

# Toolformer — 스스로 각주를 단다

핵심 아이디어: 모델이 **자기 훈련 데이터에 도구 호출을 끼워 넣고**, 도움이 된 것만 남겨 다시 학습한다.

```
원문:  "1400명 중 400명이 통과했다."
증강:  "1400명 중 400명 [Calculator(400/1400)→0.29] 이 통과했다."
       ↑ 모델이 스스로 이 각주를 달아본다
```

- 사람 라벨 0개 — **자기 생성 + 유용성 필터**
- 필터 기준: 그 호출이 **다음 단어 예측을 더 쉽게 만들 때만** 남긴다
- 지난주 STaR와 정확히 같은 계보 — 기준이 '정답'에서 '유용함'으로 바뀌었을 뿐

<p class="small">작은 모델이 훨씬 큰 모델을 이기는 수치·창발 조건은 오늘 발표 ①(Toolformer)에서 확인</p>

# ToolLLM — 도구가 많아지면 문제가 바뀐다

도구가 **몇 개**일 땐 "어떻게 부르나"가 문제였다. 도구가 **수만 개**가 되면 질문이 달라진다:

| 도구 몇 개 | 도구 수만 개 |
|---|---|
| 어떻게 부르나 | **무엇을 고르나** (검색이 필요) |
| 한 번 부르면 끝 | 여러 개 조합, **실패하면 물러나야** |

두 가지 새 개념이 등장한다:
- **도구 검색** — 스키마를 다 넣을 수 없으니 도구 자체를 검색해 후보만 컨텍스트에 (W8과 대칭)
- **물러나는 탐색** — 한 길로만 가지 않고, 막히면 되돌아가 다른 API를 시도 (W3 다수결·W5 트리 탐색과 같은 계보)

<p class="small">탐색 전략만 바꿔 성능이 얼마나 오르는지의 수치는 오늘 발표 ②(ToolLLM)에서 확인</p>

# 토론거리 — 도구 절벽 (tool cliff)

> 도구가 많아질수록 에이전트는 좋아지는가?

- 스키마도 **컨텍스트를 먹는다** — 도구가 많으면 프롬프트가 스키마로 가득 찬다
- 비슷한 도구가 많을수록 **오선택**이 는다
- 한 답: 도구를 **검색**하라 (ToolLLM). 다른 답: 도구를 **줄여라** — 좋은 도구 5개 > 어중간한 50개

발표 후 토론: *여러분의 에이전트에 도구가 몇 개일 때 절벽이 올까?*

# 발표에서 확인하고 · 실습에서 만든다

**발표 ① Toolformer** — 스스로 도구 호출을 라벨링하는 방법과, 작은 모델이 큰 모델을 이기는 수치.
**발표 ② ToolLLM** — 수만 개 API를 다루는 프레임과, 물러나는 탐색이 성능을 얼마나 바꾸는지.

**오후 실습:** W2 루프의 빈 도구 자리를 **실제 도구로 채운다** — 도구를 등록·실행하고, 모든 실패를 관찰로 되돌리는 규칙을 직접 만든다.
✅ 완료: 루프가 계산기를 **실제로 호출**해 답한다.

> 두뇌(W1) → 척추(W2) → 숙고(W3) → **손(W4)** 로 앱이 자란다. 다음은 전두엽(계획).

# 오늘 남길 세 문장

1. **모델은 실행하지 않는다** — 도구 호출은 모델의 *요청* + 하네스의 파싱·실행·재주입
2. **도구 정의가 곧 프롬프트** — 이름·설명·인자·에러 메시지 전부 모델이 읽는다. **에러도 관찰**이다
3. 도구 사용은 **배울 수도 있다** — 자기 생성+필터(Toolformer), 그리고 규모가 커지면 **선택·검색·물러나는 탐색**의 문제가 된다(ToolLLM)

**다음 주 (W5. 계획과 탐색):**
오늘 "막히면 물러난다"를 봤다 — 그럼 아예 **여러 수를 미리 내다보며** 갈 수는 없나? (Tree of Thoughts · ReWOO)
