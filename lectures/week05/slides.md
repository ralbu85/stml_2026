# 남은 결핍 — 지식

지난주(W4) 루프에 도구(W3)를 결합한 첫 완전한 에이전트가 완성되었다. 그러나 이 에이전트의 지식은 모델 파라미터 안에 든 것이 전부여서, 우리 랩 문서에 대한 질문에는 환각으로 답한다. W3 `tools.py`의 `text_search`(부분문자열 매칭)도 처방이 되지 못한다:

```
Q: "노트북 가격이 얼마였지?"
Action: {"tool": "text_search", "input": "노트북 가격"}
Observation: (0건)      ← 문서에는 "랩탑 구입 비용: 180만원"이라고 적혀 있다
```

- 문서에 답이 있어도 찾지 못한다. `"노트북" ≠ "랩탑"`, 글자가 다르기 때문이다
- 부분문자열 매칭은 글자를 비교한다. 필요한 것은 의미 비교다
- 오늘의 주제: "의미가 비슷하다"를 계산 가능한 양으로 바꾸는 장치, 임베딩

# 파라메트릭 지식의 한계

모델 파라미터 안에 든 지식(파라메트릭)만으로는:

| 한계 | 증상 | 예 |
|---|---|---|
| **수정 불가** | 재학습 없이는 지식 갱신 불가 | 어제 바뀐 조직도, 신임 대통령 |
| **출처 없음** | 왜 그렇게 답했는지 근거 제시 불가 | "어느 문서에 나와요?" → 침묵 |
| **환각** | 없는 지식은 그럴듯하게 지어낸다 | 우리 랩 내부 문서 질문 → 창작 |

- 처방: 지식을 **밖에 두고**(비파라메트릭), 필요할 때 **검색해서 컨텍스트에 주입**
- 이것이 RAG(Retrieval-Augmented Generation) — 갱신은 문서 교체로, 출처는 검색 결과로

<p class="small">출처: Lewis et al., RAG (2020) §1 — 파라메트릭 메모리의 세 가지 문제 제기 (papers/W05_RAG-Lewis PDF)</p>

# 임베딩 — 의미를 좌표로

**임베딩 = 텍스트를 숫자 벡터로 바꾸는 함수.** 잘 학습된 임베딩은 *의미가 비슷하면 벡터가 가깝다*:

```
        ▲ (2차원으로 그린 상상도 — 실제는 수백~수천 차원)
        │
        │   ● "노트북 가격"          ● "금리 인상 전망"
        │   ● "랩탑 구입 비용"
        │   ● "컴퓨터 얼마에 샀나"        ● "한국은행 기준금리"
        │
        └──────────────────────────────────────▶
             └── 가깝다 = 의미가 비슷 ──┘
```

| 문장 쌍 | 글자 겹침 | 벡터 거리 |
|---|---|---|
| "노트북 가격" vs "랩탑 구입 비용" | 없음 | **가깝다** ✓ |
| "노트북 가격" vs "노트북 반납 규정" | "노트북" 겹침 | 멀다 ✓ |

<!--

"임베딩 모델은 '비슷한 문맥에 나오는 말은 비슷한 뜻'이라는 분포 가설을 대규모로 학습한 것" — 한 줄만, 깊이는 안 들어간다.

# 코사인 유사도 — 이 과목의 유일한 수식

두 벡터가 "가깝다"의 기준 = **사잇각**. 각이 작을수록 의미가 비슷하다:

$$
\text{sim}(q, d) \;=\; \cos\theta \;=\; \frac{q \cdot d}{\|q\|\;\|d\|}
$$

```
   d₁ "랩탑 구입 비용"                 값의 범위: -1 ≤ cos θ ≤ 1
  ↗                                    1  = 같은 방향 (같은 의미)
 ↗ θ ← 각이 작다 = 유사             0  = 직각 (무관)
●──────▶ q "노트북 가격"              -1 = 반대 방향
 ↘
   ↘ d₂ "금리 인상 전망" (각이 크다 = 무관)
```

- 분자 = 내적(방향이 맞으면 커짐), 분모 = 길이 정규화(문장 길이 효과 제거)
- 검색 = "질문 벡터와 각이 가장 작은 문서 벡터 k개 찾기" — 이게 전부다

<!--

"RAG 원 논문도 검색 점수는 결국 두 인코더 벡터의 내적 하나다(정규화된 임베딩이면 코사인과 동치)" — 말로만, 수식 추가 없이.
칠판 여유 있으면 (1,0)과 (0.9,0.44) 정도로 손 계산 시범 30초.

# 코드로는 다섯 줄

```python
import numpy as np

def cosine(q, d):
    return q @ d / (np.linalg.norm(q) * np.linalg.norm(d))

scores = [cosine(q_vec, d_vec) for d_vec in doc_vecs]   # 모든 청크와 비교
top_k  = np.argsort(scores)[-k:][::-1]                   # 상위 k개 인덱스
```

- 오늘 오후 `retriever.py`의 중심부가 이 다섯 줄이다
- 임베딩 벡터는 임베딩 API 한 번이면 얻는다 — 우리는 *만들지 않고 쓴다*
- 문서 1만 청크까지는 이 완전 탐색(brute force)으로 충분히 빠르다 → 그 너머는 인덱스(현장 노트에서)

# 파이프라인 전체 — 두 개의 시간대

**① 인덱싱 (오프라인 — 문서가 들어올 때 한 번)**

```
수집 ──▶ 정제 ──▶ 청킹 ──▶ 임베딩 ──▶ 인덱스 저장
(PDF·웹)  (텍스트 추출) (조각내기)  (조각→벡터)   (벡터 DB)
```

**② 질의 (온라인 — 질문이 들어올 때마다)**

```
질문 ──▶ 질문 임베딩 ──▶ top-k 검색 ──▶ 컨텍스트 주입 ──▶ 생성
                        (코사인 상위 k) ("이 청크들을 참고해 답하라")
```

- 두 시간대를 **섞지 말 것** — 인덱싱은 미리·한 번, 질의는 실시간·매번
- 질문과 문서가 **같은 임베딩 모델**을 써야 같은 좌표계에 놓인다 (섞으면 조용히 망가짐)

# 현장 노트 ① — 청킹이 품질을 좌우한다

문서를 통째로 임베딩하면 의미가 뭉개진다 → **조각(청크)** 단위로. 그런데 몇 글자씩?

| 청크 크기 | 검색 정밀도 | 컨텍스트 품질 |
|---|---|---|
| 너무 작게 (한 문장) | 높음 | 답에 필요한 주변 맥락이 잘림 |
| 너무 크게 (한 장 전체) | 낮음 — 여러 주제가 한 벡터에 | 관련 없는 내용까지 주입 |
| **실무 기본값** | **수백 토큰** 안팎에서 시작, 데이터 보고 조정 | |

- **오버랩**: 청크 경계에서 문장이 잘리지 않게 이웃 청크와 10–20% 겹치게 자른다
- 참고: RAG 원 논문은 위키피디아를 **100단어 단위**로 잘라 **2,100만 청크**를 만들었다
- 자를 땐 문단·섹션 등 **문서의 자연 경계**를 우선 존중 (기계적 글자 수 자르기는 최후)

<p class="small">출처: Lewis et al., RAG (2020) §3 — "100-word chunks, 21M documents" (papers/W05_RAG-Lewis PDF)</p>

# 현장 노트 ② — 검색기의 다이얼

| 다이얼 | 무엇 | 실무 감각 |
|---|---|---|
| **임베딩 모델 선택** | API형(OpenAI 등) vs 오픈소스(sentence-transformers 등) | 차원·언어(한국어!)·비용 확인. **중간에 바꾸면 인덱스 전체 재구축** |
| **top-k · 유사도 임계값** | 몇 개를, 얼마나 비슷해야 넣나 | k는 3–10에서 시작. 임계값 미달이면 **"모른다"가 정답** — 억지 주입이 환각 제조기 |
| **벡터 스토어** | 벡터 저장·검색 전담 계층 | FAISS(라이브러리·인메모리) / Chroma(개발용 DB) / pgvector(기존 PostgreSQL에 얹기) |

- 오늘 실습은 스토어 없이 **numpy 배열**로 — 원리가 보이면 갈아타는 건 반나절
- k를 늘리면 재현율↑ 그러나 컨텍스트가 비대해진다 → 이 긴장은 W9(컨텍스트 예산)의 주제

<p class="small">벡터 스토어 3종은 지형 소개용 — 외우지 말 것. 규모·팀 스택 따라 고르면 된다.</p>

# RAG 원 논문 — 이름의 출발점 (Lewis et al., 2020)

**질문:** 파라메트릭(모델 안 지식) + 비파라메트릭(검색)을 **하나로 묶어 학습**할 수 있나?

```
질문 x ──▶ 질문 인코더 ──▶ 위키피디아 벡터 인덱스 ──▶ top-K 문서 ──▶ 생성기 ──▶ 답 y
           (BERT)         (2,100만 청크 · FAISS)                  (BART)
           └────────── 검색기와 생성기를 끝까지 함께(end-to-end) 파인튜닝 ──────────┘
```

- 인덱스: 위키피디아 2018년 12월 덤프, 100단어 청크 **2,100만 개**, 학습 시 top-k는 5 또는 10
- 우리가 아는 "프롬프트에 붙여넣는 RAG"의 조상 — 원조는 검색기까지 **학습**했다

# HyDE — 질문 대신 *가짜 답*을 임베딩한다 (Gao et al., 2022)

**문제:** 질문("불은 언제부터 썼나?")과 문서("호모 에렉투스가 142만 년 전…")는 **생김새가 다르다** — 벡터 공간에서 서로 멀 수 있다.

```
보통:   질문 ──임베딩──▶ ● 질문 벡터 ──── (멀다) ──── ● 실제 문서들
HyDE:   질문 ──LLM──▶ "가짜 답 문서" ──임베딩──▶ ● ──(가깝다!)── ● 실제 문서들
                       (내용은 틀려도 됨 —
                        문서처럼 '생기기만' 하면 된다)
```

- LLM에게 "이 질문에 답하는 문서를 써봐" → **환각이어도 좋다**, 그 가짜 문서를 임베딩해 검색
- 임베딩은 세부 사실이 아니라 **생김새·주제**를 잡는다 — 틀린 디테일은 벡터에서 걸러진다
- 학습 0회: 생성 모델도 임베딩 모델도 **그대로** — 검색 문제를 생성 문제로 바꾼 발상의 전환

<p class="small">출처: Gao et al., HyDE (2022) Figure 1·§1 (papers/W05_HyDE PDF)</p>

질문-문서 비대칭을 먼저 체감시키기: "질문은 짧고 물음표, 문서는 길고 서술형 — 같은 공간에서 멀 수밖에."

# 오늘의 세 줄 요약

1. **의미가 비슷하면 벡터가 가깝다** — 임베딩이 글자 매칭을 의미 검색으로 바꾼다 (수식은 코사인 하나로 끝)
